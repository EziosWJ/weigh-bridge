# 服务器监控模块需求与设计

状态：已确认。用户通过四轮需求访谈接受 Q1–Q19 推荐，以下内容为首版范围与验收依据。本文定稿时尚未开始功能实现。

后续增量：[Spec #77](server-monitoring-extension-spec.md) 已确认 Windows Server 2019/2022 原生采集、网卡 IPv4/IPv6 地址弹窗和资源监控默认关闭。下文保留首版决策历史，当前平台及启用边界遵循增量规格。

正式规格与实现切片见 [Spec](server-monitoring-spec.md) 和 [ticket 拆分](server-monitoring-tickets.md)。

## 已确认的目标与范围

- 在现有管理后台增加服务器监控菜单模块。
- 第一版只监控本项目 API 所在的一台服务器，不管理远端服务器。
- 监控范围为宿主机；API 在容器内运行时仍应监控承载容器的宿主机，不能以容器资源冒充主机资源。
- 以排查资源瓶颈为第一优先级，覆盖 CPU、内存、磁盘、GPU 与多网卡资源指标。
- 磁盘增加读写速率；各网卡增加收发速率与错误情况。
- 第一版做资源监控；Ping、端口连接、HTTP 主动可用性探测作为后续需求另行讨论。
- 第一版正式支持 Linux；其他平台明确显示支持情况，无法采集的指标不得显示为零。
- 每 5 秒采样，提供最近 30 分钟的趋势；历史仅保存在 API 实例内存中，API 重启后清空。
- 页面关闭后仍持续采样。
- 第一版在面板内显示资源异常提示，不发送站内通知等主动告警消息。
- 仅 ADMIN 可访问，菜单入口与后端接口均限制。

## 现有项目约束

- 现有 `/health`、`/ready` 与 `/metrics` 面向 API 存活、数据库就绪和应用指标，不是宿主机资源监控实现。
- 当前开发 Compose 未配置主机资源挂载、主机网络命名空间或 GPU 透传，API 容器以非 root 用户运行；本模块采用下述已确认的宿主机采集进程方案。
- 现有动态菜单由数据库和角色菜单关系驱动，前端页面路由单独注册。
- 菜单可见性不替代 API 授权；监控接口需显式校验 ADMIN，沿用现有业务角色校验方式。
- 不因短期趋势引入时序数据库或写入现有业务数据库；菜单种子变更仍遵守现有 PostgreSQL/SQLite migration 约定。

## 已确认的指标与展示规则

| 区域 | 指标 |
| --- | --- |
| 主机 | 主机名、系统版本、运行时长 |
| CPU | 型号、核心数、总体及逐核利用率、系统负载 |
| 内存 | 总量、已用、可用、占用率、Swap 使用情况 |
| 磁盘 | 按挂载点展示文件系统容量；按块设备展示读写速率、IOPS |
| 网络 | 各网卡收发速率、累计流量、链路状态、错误与丢包 |
| GPU | NVIDIA 多卡，逐卡展示型号、利用率、显存、温度及功耗；字段以设备支持情况为准 |
| 进程 | CPU、内存占用 Top 10，显示进程名、PID 和占用量；第一版提供查看功能 |

- 默认隐藏回环及 veth 接口，提供显示全部接口的开关。
- 网卡收发速率使用 MiB/s；能取得链路速率时补充带宽占用率。
- 不直接合计所有接口流量，避免虚拟接口、聚合接口及成员接口重复计算。
- 各区域独立展示正常、无设备、不支持或采集失败；部分采集失败不阻止其他区域展示。
- 保留旧值时标注采集时间；超过 15 秒没有新样本时标为过期，趋势保留缺口。
- NVIDIA 部分设备或环境不支持完整指标，不能将不支持的字段填成零，见 [NVIDIA 官方文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

## 指标计算口径

| 指标 | 口径 |
| --- | --- |
| 总体 CPU 占用 | 以整机总算力为 100%，根据采样窗口计算 |
| 进程 CPU 占用 | 以整机总算力为 100%，与总体 CPU 使用相同窗口；排行按该值排序 |
| 逐核 CPU 占用 | 每个逻辑核单独计算，以该核算力为 100% |
| 系统负载 | 展示 Linux 的 1、5、15 分钟负载，使用原始负载值，不标为百分比 |
| 内存已用 | 总量减可用量；占用率为已用量除以总量 |
| 进程内存占用 | 以常驻物理内存量排序，展示占用量 |
| 文件系统占用率 | 已用空间除以已用空间与普通用户可用空间之和；总量、已用量、可用量分别展示 |
| 磁盘读写速率、IOPS | 相邻有效样本的对应累计计数差值除以实际采样间隔 |
| 网卡收发速率 | 相邻有效样本的字节计数差值除以实际采样间隔；显示单位 MiB/s，1 MiB 为 1,048,576 字节 |
| 网卡带宽占用率 | 链路速率已知时，将收发速率转换为 bit/s，分别与链路速率比较 |
| GPU 指标 | 使用设备实际提供的利用率、显存、温度与功耗；支持情况按字段展示 |

Linux 的 `MemAvailable` 是可供新应用使用的内存估算值，包含可回收部分，见 [Linux 内核说明](https://www.kernel.org/doc/html/latest/filesystems/proc.html)。

设备新增、计数重置或采集进程重启后重新建立速率基线。首个速率样本显示“采集中”，不产生负速率或瞬时尖峰。无法取得的值按支持或采集状态展示；未配置 Swap 时明确显示该状态。

## 异常提示规则

第一版采用固定阈值，页面说明各项触发与恢复规则。

| 项目 | 触发条件 | 恢复条件 |
| --- | --- | --- |
| 总体 CPU | 占用率 ≥90%，持续 60 秒 | 占用率 <85%，持续 30 秒 |
| 主机内存 | 占用率 ≥90%，持续 60 秒 | 占用率 <85%，持续 30 秒 |
| 各文件系统 | 占用率 ≥90%，立即提示 | 占用率 <85%，恢复提示 |
| GPU、网卡 | 展示设备状态与错误信息 | 随有效的新状态更新 |

GPU 高利用率与网络高流量本身不触发资源异常提示。采样中断时中止对应指标的持续时间判断，显示采集状态；恢复采样后重新计算连续时间，不把缺口视为连续正常或连续异常。

## 菜单与页面组织

- 菜单位置：系统监控 → 服务器监控。
- 顶部展示主机信息、采集时间及 CPU、内存等资源概览。
- 下方展示最近 30 分钟趋势、磁盘、网卡、GPU 与进程排行。
- 网卡、磁盘、GPU 等多设备可切换查看趋势。
- 页面按 5 秒周期刷新已采集数据；页面关闭后后台仍按既定周期采样。
- 历史尚未积累到 30 分钟时照实展示已有数据，采集缺口不连接为连续曲线。
- 页面各区域显示支持情况与采集状态；旧值必须附带采集时间和过期状态。
- 菜单入口仅 ADMIN 可见；直接访问页面和后端接口也须落实 ADMIN 限制。

## 已确认的采集部署方式

- API 直接部署在 Linux 宿主机时，在 API 内部采集。
- API 通过 Docker 部署时，在同一台宿主机上额外启动采集进程，通过本地 Unix socket 供 API 读取。
- 两种方式共用宿主机指标的业务含义；Docker 部署需要管理额外采集进程。
- Docker 部署的采集进程提供最新样本，由 API 保存短期历史；Unix socket 的目录与访问权限随部署说明明确配置。
- 采集使用专用用户及必要读取权限；部分权限不足时明确显示覆盖不完整。
- 采集设置超时，同一采集任务不重叠运行；各区域独立处理失败。
- 决策原因见 [ADR-0011](adr/0011-host-resource-collection-boundary.md)。

## 历史与重启行为

- API 按采集时间保留最近 30 分钟历史，淘汰窗口外样本，内存占用有界。
- 历史归属当前 API 实例；多个实例的历史独立。
- API 重启后清空历史，并逐步积累新样本。
- 宿主机采集进程重启时，API 保留已有历史；中断期间留下缺口，恢复后继续追加。
- 各区域最近一次有效采集超过 15 秒时标为过期；失败或不支持的字段不因其他区域更新而变成有效新值。

## 验收清单

以下为后续实现的验收要求，不代表已通过验证。

- [ ] ADMIN 可查看菜单、页面与数据接口；普通用户和未登录请求按现有认证与授权契约拒绝。
- [ ] 直接部署与 Linux Docker 部署均取得宿主机指标；Docker 场景对照宿主机网卡、挂载点及设备身份，确认采集范围。
- [ ] CPU、内存、磁盘容量、速率及 IOPS 按约定口径计算；使用确定的采样计数验证差值、实际时间间隔与单位换算。
- [ ] 多网卡逐卡展示；默认筛选、显示全部、链路速率未知与设备新增/计数重置行为符合约定。
- [ ] 多块磁盘、多文件系统和多 GPU 分别展示，设备趋势切换正确。
- [ ] CPU、内存进程 Top 10 排序正确；读取权限不足或进程退出时保留其他有效结果并说明覆盖情况。
- [ ] 无 GPU、驱动或字段不支持、部分采集失败、采集超时与过期均按区域展示，不将缺失值填零。
- [ ] CPU、内存的持续触发与恢复、文件系统即时触发、采样中断后的判断重置符合规则。
- [ ] 历史窗口淘汰、首屏采集中、数据缺口、API 重启与采集进程重启行为符合约定。
- [ ] 页面关闭后持续采样，同一采集任务不重叠，采集故障不影响其他 API 功能。
- [ ] NVIDIA 指标完成真机验证，并记录显卡型号、驱动版本、支持与不支持的字段；缺少硬件时如实列为未验证，不能宣称该项验收通过。
- [ ] Docker 部署说明包含采集进程的启动、升级、Unix socket 权限及采集状态检查方法。

## 实施与验证入口

后续实现遵循现有项目模块边界与 Taskfile：后端改动执行 `task backend:check`；前端改动执行 `task frontend:lint` 与 `task frontend:build`；新增菜单种子 migration 时先执行 `task db:migrate`，并覆盖 PostgreSQL、SQLite 两套 migration。联调按需使用 `task api` 或 `task dev`，以 `/health` 和 `/ready` 检查运行与数据库状态。具体采集库、代码布局及接口字段在实现时按本需求选择，不新增独立时序数据库等基础设施。
