# 车牌候选联动：依赖核对与模拟设计

本文件记录 #9～#12 的设计和现场验收步骤；实现及验证进度见[当前状态](../next.md)。厂家推送图片不保存或处理；无图事件可成为有效候选。#8 保存车牌元数据、返回 ACK 并按摄像头与请求摘要去重，不需要厂家图片前置条件。

## 候选查询设计

`GET /api/weighing/plate-candidates?scale=<地磅编码>&after=<游标>` 使用 `weighing:read` 和本厂地磅授权，返回 `items`、`nextCursor`、`serverTime`。候选由本厂启用且绑定的摄像头已成功保存的事件构建，返回事件记录 ID、相机 ID 和名称、设备时间及服务端接收时间，不返回厂家图片或引用。只允许有效车牌、设备时间合理且新鲜的事件自动预填；旧事件及未来异常时间不得自动预填。正式证据使用现有 RTSP 抓拍。

同一规范车牌按服务端首次接收时间的近邻间隔不超过 15 秒合并，保留全部来源；不同车牌独立。每个事件自首次接收起 60 秒过期，重传不能刷新时间；迟到设备时间超过 60 秒不自动预填。按最近接收时间排序最多展示 5 项。每次查询基于完整有效窗口重算，候选 ID 使用该组最早事件记录 ID；窗口内合并可能导致 ID 随过期变化，客户端须以来源事件去重而非假定 ID 永久不变。

PostgreSQL BIGSERIAL 分配顺序不保证提交顺序，因此事件写入和水位读取共用事务锁；隔离 PostgreSQL 测试覆盖未提交事件的水位读取。初始化和下一辆车均先取得服务端水位，新周期仅自动接收水位之后的合格事件；历史候选可以人工选择。轮询请求串行，过期响应丢弃，恢复连接后保留输入所有权，不重放动作。

## 工作台与留痕设计

输入所有权分为空、建议、人工、已核对。只有有操作权且没有焦点、草稿编辑、定位任务、采样、核对窗口、未决提交或完成状态时，新周期的新候选可自动填入；不同车牌只提示冲突，同车只更新来源。用户编辑或选择立即保护输入，选择不触发查找。仅明确点击核对并成功查找后标记已核对；仅清理草稿成功且操作员点击办理下一辆车后重置周期。断网或无相机保留人工入口。

人工核对时通过 `POST /api/weighing/plate-confirmations` 提交确认车牌、原候选、事件记录 ID 和人工修正标记。服务端核对事件存在、来源绑定、本厂有效相机、候选内容及时效，并从数据库读取来源和时间，保存服务端核对时间；采样引用同账号、地磅和会话的核对记录，并检查来源仍有效。禁止信任客户端的来源标签、相机名称或时间。核对值与候选不同时标记人工修正。冻结快照保留原候选、确认值和来源事件，首回磅各自保留；手录保持原路径。修改已定位车牌仍须重新查找并使旧采样失效。

## 现场验证

软件与隔离数据库验证见[当前状态](../next.md)。模拟摄像头、模拟仪表及软件检查不证明真实设备行为。

单摄现场验收：先在授权测试场地核对设备与 Server 时钟和绑定；真实车辆触发事件并确认 ACK 与单条记录，检查工作台候选及人工核对，按现有流程采集 RTSP 图片和完成首磅，检查历史来源；离线后验证人工路径。真实车辆操作由现场人员执行。

第二台安装后：核对两台绑定及时间，分别触发同车与不同车牌，检查合并和冲突；首磅后办理下一辆车，再以反向来车查找待回磅任务并完成回磅，核对两次来源及正式证据；检查离线恢复和延迟补传。记录脱敏时序和结果，不将模拟结果当作现场通过。
