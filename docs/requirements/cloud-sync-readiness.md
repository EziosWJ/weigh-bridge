# 厂云摘要同步：实施准备与协议缺口

2026-11-01 更新：云端已发布摘要规则版本 2、上传错误类别和对账接口，厂端已按发布包完成实现与软件验证，见[厂端实现与验证](cloud-sync-v4-delivery.md)。本文保留实施前的就绪判定、差距盘点和协议确认清单，作为追溯记录。

2026-10-31。本文是实施前核对记录，不新增业务规则；目标仍以[厂云同步契约](cloud-sync-contract.md)为准，本厂业务细则见[业务规则](weighing-business-spec.md)。本轮未修改代码、未新增 migration，也未连接任何数据库。

## 1. 结论与判定依据

云端新协议尚未形成可实现的字段级约定：仓库内没有摘要规范化规范、没有上传接口的新字段定义、没有对账查询接口、没有错误类别枚举，也没有可复用的摘要测试向量。按“不自行制定不兼容摘要格式”的约束，厂端本轮不能开始第 1、2 项开发，第 3 项同步模块也只能在接口语义确定后实施。

判定依据：

1. 共享契约已把规则留给实施前细化：摘要版本、规范化字段与测试向量、接口字段、错误类别、分页和对账实现“仍需双端细化及验证”；摘要“具体规范和跨版本处理须在实施前确定”。见[契约](cloud-sync-contract.md)的“过磅单上送与确认”“实施前需细化”两节。
2. 云端接口设计首段明确：该文件只描述现行版本 3（兼容版本 2），“不是已确认的摘要同步和对账新方案的接口设计”“尚未实现，新协议接口须另行细化”。见云端仓库 `docs/requirements/weighbridge-sync-api-design.md`。
3. 云端代码只有现行去重，不是新方案：云端对收到的 JSON 自行 `json.Marshal` 后计算 SHA-256，存为 `payload_hash`，并用随机 `changeId` 去重（`fenchichun/server/internal/weighbridge/repository.go:73-88`、`:153`）。契约要求的是厂端计算摘要、摘要本身作为变化标识、云端保存厂端摘要，两者语义不同。
4. 云端没有对账能力：现有路由只有 `GET /api/v1/weighbridge/sync/master` 和 `POST /api/v1/weighbridge/sync/changes`，没有按单号或日期查询已接收变化、最新摘要、缺单或历史编码确认的接口。
5. 没有摘要测试向量：云端仅有版本 3 业务样例 `server/internal/weighbridge/testdata/change_v3_issue.json`，其中 `changeId` 是 32 位占位值，没有摘要规则版本或期望摘要；厂端 `server/internal/weighing/testdata` 中没有对应文件。
6. 云端工作区只有三份文档的状态说明修改，没有提交新摘要算法、新接口或测试向量。

只要上述任一项缺失，任何上传、重试或对账代码都必须自行定义字节级格式，后续将无法与云端比对，因此不属于可安全推进的范围。

## 3. 必须先确认的协议缺口

以下问题需要云端先定稿。厂端不预设答案；括号内为该项影响的本厂行为。

### A. 摘要规范

1. 规则版本如何表示（字符串还是整数）、当前值，以及“不可比较”的判定条件。（决定对账显示“待核查”还是“冲突”。）
2. 出单、作废、重开各自纳入摘要的字段清单，是否包含 `previousSiteCode`、`previousTicketNo`、上版重量与上版净重；`schemaVersion` 是否仍参与。（决定摘要输入与载荷是否一致。）
3. 规范化序列化算法：规范 JSON（键排序、分隔符、转义、Unicode 处理）还是长度前缀的字段拼接；字段顺序、缺失字段与空字符串、`null`、布尔值的表示。（决定字节级结果。）
4. 重量、时间与编码的表示：重量用十进制吨字符串还是整数千分吨；时间用 RFC3339 的哪种精度、是否统一换算为 UTC；空文本与缺失值的区分。（决定摘要稳定性。）
5. 摘要编码：小写十六进制、固定 64 位，还是其他编码。（决定变化标识字段长度与唯一约束。）
6. 摘要是否直接作为请求中的 `changeId` 传输，是否另设 `digest`／`digestVersion` 字段，是否仍发送 `schemaVersion`。（决定请求结构与去重键。）
7. 测试向量：至少覆盖出单（含可选字段为空与中文）、作废、重开（含跨厂区编码）、不同时间精度与重量写法，并提供期望摘要。厂端将逐条复用，不自行生成基准。
8. 跨规则版本比较的展示与处理语义：旧版本摘要是否只读展示、何时要求人工核查。

### B. 变化上传接口

1. 新端点的路径、方法、请求体字段及大小上限；是否沿用 `/api/v1/weighbridge/sync/changes` 但提升协议版本。
2. 成功响应的字段与语义：返回哪个摘要、单号及确认时间；是否必须逐项核对。
3. 错误类别的稳定枚举与 HTTP／业务码映射：临时故障、前序未完成、配置或数据错误、单号或变化冲突、协议版本不支持、厂区编码无效。厂端需要可区分的机器可读类别，而不是只靠状态码。
4. 幂等语义：同一摘要重复请求返回原确认还是错误；云端是否保存完整载荷；同一摘要搭配不同内容如何发现与返回；接收历史是否按“厂区编码＋单号＋变化类型＋摘要”唯一。
5. 顺序与“最新摘要”：云端如何拒绝较早状态覆盖较晚状态；是否按变化类型顺序校验；重开的原单未作废时返回哪个类别。
6. 厂区改码后旧编码的未确认变化如何处置；按旧编码与摘要只读查询历史确认的接口与权限。
7. 现有版本 2／3 请求在新端点或同一端点上的行为；厂端升级时未发送的旧变化是否允许继续发送。（契约说新方案不要求兼容，需要明确“旧队列不自动改写、不被新 worker 处理”的边界。）

### C. 对账查询接口

1. 单张查询与批量查询的端点、参数（厂区编码、单号、日期范围）、分页与单次上限。
2. 响应是否包含：单据是否存在、已接收变化列表（类型、摘要、规则版本、确认时间）、单据最新摘要、出单变化是否存在、作废与重开状态及关联、云端记录是否自相矛盾。
3. “云端缺单”与“云端有单但找不到出单变化”是否能分别识别；厂端需要据此决定自动补传还是提示人工处理。
4. 批量日期范围的基准：出单日期、发生变化日期还是云端接收时间；最近 7 天“发生过变化”的判定口径。
5. 查询失败、超时、限流与部分结果的表示；厂端必须能显示“结果未知”，不能当作一致。
6. 历史编码只读确认查询的参数与返回；是否限制访问频率。
7. 对账请求是否需要携带厂端摘要版本；不同版本时返回什么。
8. 时间字段的时区与精度，以及云端时钟与厂端不一致时的判定。

### D. 本地契约边界（无需云端，但需确认后实施）

1. 新协议下现有 `wb_ticket_sync_change` 的随机标识行如何处理：保留只读、停止上传，还是另行迁移。契约要求现有测试数据先保留，不能自动清理。
2. 同步状态字段与日志保留分类的最终命名；冲突与核查记录单独存储。
3. 自动对账固定时间、时区与退避参数的配置键；这些属于本厂配置，不进入云端协议。

## 4. 协议确认后的实施顺序

以下为计划，不是本轮已完成内容。

1. **共享规范与向量**：云端发布摘要规范和测试向量文件；两端各自内嵌同一份向量，先让摘要计算测试双端一致。
2. **摘要模块**：厂端新增独立的规范化与摘要计算模块，输入为已保存的完整变化载荷，输出规则版本与摘要；不做数据库写入。测试覆盖向量全集、字段空值与时间精度。
3. **outbox 演进**：新增 Goose migration，为变化增加摘要、规则版本、状态细分、尝试次数、下次尝试时间、冲突与核查记录；新变化在业务事务内计算并保存摘要与载荷；旧行保留。
4. **上传客户端**：按协议发送原载荷与原摘要；解析机器可读错误类别；同单据顺序与重开依赖沿用现有 SQL 并在新状态上扩展；临时故障按尝试次数退避；管理员手动重试只前移本人变化且不跳过前序。
5. **对账**：单张与批量查询、结果落库、每日定时与启动补做；缺单补传、同摘要自动确认、冲突暂停与重新核查；改码提示与旧编码只读确认查询。
6. **同步模块**：后端 API 与权限（普通操作员只读简要状态，管理员详情、核对、处理），前端“单据同步／基础资料同步／同步日志”三个菜单；资料页保留原主动同步入口，两处调用同一完整同步且不触发单据上传。
7. **日志拆分**：普通尝试日志可清空；冲突、核查结论与处理记录单独保留。
8. **验证**：隔离 PostgreSQL 与隔离假云端，先跑契约向量，再跑断网、回执丢失、重复确认、作废与重开顺序、冲突暂停与重新核查、改码历史确认、开关切换；具备真实云端隔离实例时再做双端联调。

## 5. 验证场景与判定

| 场景 | 预期可观察结果 |
| --- | --- |
| 摘要向量一致 | 两端对同一输入得到完全相同的规则版本与摘要；任一字段、空值或时间写法变化都会改变结果 |
| 断网补传 | 业务正常出单，队列保留；恢复后按原顺序、原载荷与原摘要上传 |
| 回执丢失 | 原载荷与摘要重试；云端返回原确认后本地才标记完成 |
| 重复确认 | 重复请求不产生第二张单据，不改变已确认状态 |
| 作废与重开顺序 | 重开在原单出单和作废均确认前保持等待；前序失败时后续不越过 |
| 冲突暂停与重新核查 | 仅相关单据暂停；差异与核查结论保留；重新核查仍需依赖满足 |
| 改码历史确认 | 旧编码未确认变化不静默改写；可按旧编码与摘要只读确认；新单按新编码上传 |
| 同步开关切换 | 关闭后停传、停止自动对账、队列不删；重新开启并完成资料同步后继续 |
| 对账查询失败 | 显示结果未知或待核查，不显示一致 |

## 6. 本轮未完成与下一步

本轮未修改任何代码或数据库，原因是缺少第 3 节 A～C 的字段级规范。下一步需要云端先交付：

1. 摘要规范正文与测试向量文件；
2. 上传接口字段与错误类别枚举；
3. 对账查询（单张、批量、历史编码确认）接口字段；
4. 新协议版本标识及旧队列处置边界。

收到上述内容后，可按第 4 节顺序直接开始厂端实现；在此之前，本厂现有版本 3 实现的顺序、原样重试和开关行为保持不变，不进行推测性改造。
