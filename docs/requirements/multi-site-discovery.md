# 多厂区与 Agent 互斥需求

日期：2026-10-21。状态：Q1～Q18 已逐轮确认，用户随后明确启动实施；代码及受控软件验证完成，真实工控机升级和设备现场验收未执行。实际结果见[实施记录](multi-site-delivery.md)。以下规则为本轮确认范围。

## 问题与现场事实

客户有两个厂区，每厂各一台地磅，各有独立工控机、打印机等现场设备，需要独立办理称重业务。当前“互相抢”发生于同一地磅的真实 Agent 与 mock 同时启动。

现有系统按单厂区、单地磅实现：Server 只有一组 Agent 身份和连接，新连接替换旧连接；真实打印 Agent 与 mock 默认共用身份，且均自动重连，因而持续互踢。前端默认选择首个启用地磅，工作台窗口名称全局固定；车牌未完成任务唯一性、列表和详情等没有厂区范围。仅增加 Agent 编号或第二条地磅记录不能满足新需求。

## 厂区、设备与业务归属

- 使用一套 Server 与数据库管理两个厂区，每台地磅归属于一个厂区，其工控机、Agent 和打印机对应同一现场。当前每厂一磅，厂区与地磅分别保留身份。
- 任务、称重依据、单据、设备状态、抓拍及打印遵守厂区边界；不同厂区分别处理，不能因共用 Server、用户或浏览器而互相覆盖。
- 同一运输任务的两次称重在同一厂区完成；跨厂运输分别建立任务，不拼接两厂称重依据形成同一单据。
- 同一厂区内同车牌最多一笔未完成任务；不同厂区允许各有一笔同车牌未完成任务。同车不同趟次仍分别建任务。
- 物料、供货商、客户、承运商等基础资料共享，沿用现有资料管理权限。有权限人员统一维护，修改对两厂生效；普通称重操作员只选用。

## 授权与服务端隔离

- 在现有用户管理中提供厂区授权，允许用户获多个厂区授权；区分可查询与可操作范围，跨厂查询不自动赋予跨厂操作权。
- 厂区授权与现有业务动作权限共同生效。例如用户可操作甲厂、可查询乙厂，即使已有称重确认权限，也不能在乙厂确认称重。
- 操作员不能查看或操作未授权厂区的任务、称重记录和单据；管理人员可在授权范围内跨厂区查询、筛选、汇总和导出。
- 列表、详情、汇总、导出、图片读取、会话、采样、首磅／回磅／重称、终止、更正、作废、打印及结果核实等受影响入口均在服务端校验厂区范围。修改 URL、记录 ID 或请求参数不能绕过授权。
- 复用现有登录、JWT、RBAC、响应、错误和审计机制，不改变无关用户身份及系统管理逻辑。

## 厂区面板与工作台

- 新增独立菜单，进入后台布局内的厂区面板页；只有一个授权厂区的用户也使用此入口。
- 只展示已授权厂区，未授权厂区不返回面板信息；无授权显示明确空状态。
- 以 panel／卡片展示厂区名称及其地磅、授权范围内的 Agent 状态，提供进入对应称重台的入口。仅获查询授权的用户不提供操作工作台入口，进入还需满足现有业务权限。
- 点击面板打开对应地磅的独立工作台窗口，明显显示厂区与地磅。窗口固定归属，不在办理中静默切换现场。
- 获多厂操作授权的用户可同时打开不同厂区工作台；同地磅重复进入可复用对应窗口，不覆盖另一厂区。菜单搜索、登录后的工作台入口、任务跳转同步遵守新入口及归属。
- 同一地磅仍只有一个窗口持有操作权，接管须明确操作，沿用租期与审计；不同地磅的会话分别持有、续期和释放。

## Agent 互斥、踢出与恢复

### 连接与切换

- 每台地磅同一时间只允许一个 Agent 在线，由同一代理连接承担采集、识别、抓拍和打印通信；真实 Agent 与 mock 互斥，不拆分采集和打印连接。
- 两厂 Agent 可同时在线，连接、状态、命令、图片、未决回复和设备版本分别绑定地磅。某厂离线、重连或被踢出，不影响另一厂。
- 同磅已有 Agent 在线时保留当前连接、拒绝后来者并明确提示冲突；拒绝不覆盖当前状态、不使当前有效采样失效、不打断原请求，也不自动接管。
- 后台提供踢出当前 Agent 的操作；替换时先踢出，再启动目标 Agent 或 mock。踢出针对选定连接，不得因状态变化误踢新连接或其他厂区。
- 普通网络中断仍按既有规则自动重连，不得误判为踢出。

### 权限与退出

- 新增独立的“踢出 Agent”权限，同时校验目标厂区操作授权；普通操作员默认无此权限。审计记录操作者、厂区、Agent 和时间。
- 真实 Agent 和 mock 收到 kick 后结束整个进程，停止本次自动重连；mock 的控制页面服务一并结束。正常退出不得导致守护服务立即拉起。
- 踢出只结束本次运行，不永久封禁身份；允许维护人员手动启动或工控机重启后重新接入，仍受同磅单连接规则限制。
- 后台区分指令发送／断连和客户端确认退出。网络异常或旧客户端未确认时，不得声称进程已退出，应显示“已断开，退出未确认”等真实结果。
- 本地维护服务与 CUPS 不属于被踢出的通信 Agent 进程；维护服务仍可用于排障和明确的人工启动。

### 在途业务

- 踢出立即生效：进行中的采集失败、已采集但未确认的样本失效；稍后重连不能使旧样本恢复可确认。
- 已提交成功的业务不因踢出撤销；提交结果不明时先查询原请求结果，不自动补办历史确认。
- 无最终回执的打印保留“结果未知”，人工核实，不自动重发；保留打印尝试账本及防重记录。
- 已交给 CUPS／打印机的作业可能继续出纸；退出 Agent 不等于取消纸张打印，也不自动证明失败或未打印。

## 单据、历史数据与配置

- 纸单显示厂区名称，单号保持系统内唯一；打印、补打固定送至单据所属厂区打印机，同时校验该厂区的打印操作权限。
- 现有任务及单据全部归入原厂区，新增厂区从空业务数据开始；共享资料保留。不能清空旧单据、改写历史重量或丢弃打印防重账本。
- 历史单据内容和版本依据保留；升级添加归属不重新计算旧单据。新形成单据保存厂区展示信息，后续配置修改不改写出单依据。
- 新增 Goose migration 调整归属、授权和车牌唯一约束等，保留历史 migration；PostgreSQL 与 SQLite 行为一致，API 启动不自动迁移。
- 两厂分别配置地磅和有效 Agent 身份映射，保留原厂区已有有效身份、密钥及账本；真实密钥只放本地忽略配置，示例用占位符。
- 厂区实际名称可在实施时配置，当前称“原厂区／新增厂区”，不影响业务边界。

## 交付与阶段边界

本轮计划交付多厂区业务隔离、用户授权、厂区面板菜单及多窗口工作台、多地磅连接管理、重复连接拒绝、后台踢出和两个客户端退出行为，以及相关数据升级、验证与文档。

真实仪表、摄像头驱动沿用后续接入计划。当前真实 Agent 仅打印可用，仪表和摄像头未接入；mock 在线时打印也由 mock 处理，不能同时借真实打印 Agent 出纸。切换当前真实 Agent 后，称重采集仍不可用。软件验收不能描述为真实称重设备验收。

人工确认、吨制重量、Server 校验正式记录、断网暂停正式确认、同磅接管及打印结果人工核实等既有规则继续适用。

## 验收条件

下表保留验收预期；已执行的检查与准确结果见[实施记录](multi-site-delivery.md)，软件验证不等同于真实现场验收。

| 场景 | 预期 |
| --- | --- |
| 两厂同时在线与办理业务 | 两台地磅分别采集和打印；状态、命令、会话与回复互不影响 |
| 同磅真实 Agent 与 mock 并发启动 | 仅一个连接在线，已在线者保留，后来者明确冲突；原状态、采样和请求不受影响 |
| 有权限人员踢出 | 仅作用于选定地磅连接，留下审计；收到 kick 后整个进程退出，不重连、不被立即拉起 |
| mock 收到 kick | 连接运行与 HTTP 控制服务均结束，不仅退出一个 goroutine |
| 无权限／越厂踢出 | 服务端拒绝，不影响目标 Agent |
| kick 未确认或连接变化 | 不虚报进程已退出，不误踢新连接 |
| 踢出后恢复与普通断网 | 人工启动或重启工控机可重新接入；普通网络故障保留自动重连 |
| 踢出时采集／确认／打印 | 未确认依据失效、已提交记录保留；无回执打印未知、不重发，防重账本保留，CUPS 作业可能继续出纸 |
| 面板与授权入口 | 只显示已授权厂区，无授权有空状态；跨厂查询不赋予操作入口 |
| 直接访问未授权记录或设备 | URL、ID、筛选参数和请求体均不能越权；详情、图片、导出及业务操作统一校验 |
| 列表、汇总、导出 | 仅含授权查询范围；管理人员按厂区查询汇总，不自动获得操作权 |
| 同浏览器两厂工作台 | 窗口及状态分别绑定厂区地磅；同磅占用、明确接管继续生效 |
| 同车未完成任务与跨厂回磅 | 同厂冲突、不同厂可分别建任务；不能跨厂拼接二磅 |
| 共享资料 | 授权人员维护后两厂可用；普通操作员不因此获得修改权限 |
| 单据与打印 | 新单纸面显示厂区、单号全局唯一；打印／补打只投递原厂区并校验权限 |
| 升级与兼容 | 旧业务归原厂、新厂无旧业务；历史依据、有效身份及账本保留，两种数据库约束一致 |
| 真实设备限制 | 如实显示仪表和摄像头未接入，不伪造重量、抓拍或验收状态 |
