# Agent 协议与独立 mock 讨论

状态：Q1～Q8 已确认；用户已授权发布 Spec 后实施，跟踪 [Issue #3](https://github.com/EziosWJ/weigh-bridge/issues/3)。实现及可执行验证完成，限制见 [交付记录](agent-mock-delivery.md)。

## 已确认

2026-10-19，用户接受首轮 Q1、Q2 推荐，并对 Q3 明确简化：

- agent-mock 为带独立 Web 控制台的程序，与未来真实现场 Agent 使用同一套 Server 通信协议。
- 重量、稳定／故障、识别候选、画面／抓拍和打印设备模拟纳入边界设计；通信覆盖上报及 Server 下行命令。实时画面的本轮实现范围待定。
- 系统负责人工核对、称重确认、业务校验、单据和打印任务；Agent 提供设备数据及命令执行结果。
- 系统不再区分模拟与正式数据，模拟行为由 Agent 决定；不增加 Server 测试身份登记或测试／正式两套流程。agent-mock 用于开发和上线前测试，采用简单方案。
- 统一来源不代表真实设备已经验收；现场驱动、实际抓拍、物理打印的完成状态须如实记录。

第二轮确认：

- Q4：Agent 端采集并发送报文；agent-mock 应先发送持续 3～5 秒的不稳定重量，再转为稳定，系统工作台实时显示变化。采集触发方式、稳定后的依据冻结时机仍待下一轮明确。
- Q5：本轮采用最新现场图片与采集抓拍；mock 提供示例图片或上传图片，实时视频留待现场摄像头阶段。
- Q6：采用配置文件中的 Agent 编号、地磅编号及连接密钥，由 Agent 主动通过 WSS 连接 Server；本轮一台 Agent 对应一台地磅，不建设注册审批及设备管理页面。

第三轮确认：

- Q7 补充：每条重量报文由 Agent 同时给出重量和稳定状态（例如 `weight: 32.560`、`unit: t`、`stable: true`）。系统依据 Agent 上报展示状态，不自行从重量波动推断稳定。
- 不稳定时禁止采集；稳定后允许操作员采集、核对并确认，稳定状态不自动生成称重记录。再次失稳或连接中断时，尚未确认的采集依据失效。
- Q7 操作顺序采用推荐，并按用户补充明确稳定状态来源：mock 设置目标重量、车牌和图片后模拟上磅，先波动再稳定并持续上报；系统点击采集获得对应重量与抓拍，再人工确认；mock 模拟下磅后重量归零。
- Q8 已接受：系统经 Server 下发打印任务，mock 展示单据内容，由 mock 页面选择回报成功、失败或暂不回报；保留系统既有打印记录、结果未知的人工核实及补打规则，本轮不驱动物理打印机。

## 当前实现与迁移影响

- Server 的 `/test/conditions`、`/test/samples` 接受浏览器模拟输入；采样及确认受 testMode、simulated 来源和模拟条件版本限制，任务固定为 test。
- 浏览器生成识别候选，Server 使用内置图片构造采集依据；当前没有现场 Agent 上报或抓拍上传接口。
- 打印已有服务端尝试记录及人工结果反馈，但实际调用浏览器打印，没有 Agent 下行执行。
- Agent 和 protocol 仍为预留目录；WSS 是已有通信方向，具体协议尚未实现。
- 因此需要调整采集入口、来源限制及前端控制，而非仅搬动模拟设置页面；已有历史单据与依据不得因迁移被改写。
