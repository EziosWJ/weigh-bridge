# Spec：完善公开公告、站内公告与实时站内通知

## Problem Statement

脚手架目前只有要求登录的站内通知，管理员可以手动发送通知，角色变更也会触发通知。未登录访问者无法看到系统公告；已有“全体用户通知”按发布时的启用账号建立接收记录，不能承担面向未来用户持续可见的公告职责。

用户需要进入系统就能了解公开信息，登录后查看有效站内公告及个人通知。现有铃铛每 30 秒轮询，通知到达与已读状态在不同页面间不能及时同步。业务通知接入仍绑定角色变更的持久化实现，其他项目复用缺少明确入口。

需要形成适合单实例脚手架的完整站内消息能力，提供明确的消息边界、公告生命周期、实时体验与业务接入方式，继续兼容 PostgreSQL 和 SQLite。

## Solution

区分三类消息：公开公告无需登录即可查看；站内公告面向已登录用户，发布后新建用户也能看到有效公告；站内通知按接收人保存个人阅读状态，接收范围为指定用户或发布时已有且启用的全体用户。

管理员维护公告草稿、立即发布、可选到期时间与主动撤下。公开公告出现在登录页和登录后的公共布局，站内公告出现在登录后的公告栏及公告列表；公告不提供逐人已读或签收。个人通知保留铃铛、未读数、分页列表和详情已读，并支持业务可选站内跳转。

采用 SSE 推送变化，正常网络及约定验证规模下，发布成功后 2 秒内更新在线页面，不使用消息轮询或轮询降级。数据库保存完整事实，断线、重启后重新查询状态，离线消息不逐条补弹。业务通知与业务操作、审计原子提交，只有提交成功后才广播。

## User Stories

1. 作为未登录访问者，我希望打开登录页即可看到有效公开公告，以便提前了解维护、服务说明等公开信息。
2. 作为未登录访问者，我希望只能访问公开公告，以便系统的站内信息与个人消息保持隔离。
3. 作为已登录用户，我希望在公共布局继续看到公开公告，以便登录后仍能了解公共信息。
4. 作为已登录用户，我希望看到当前有效的站内公告，以便了解只面向系统用户的信息。
5. 作为新注册用户，我希望看到注册前已发布但仍有效的站内公告，以便获得当前需要知道的信息。
6. 作为用户，我希望能够打开公告列表与详情，以便完整阅读公告正文。
7. 作为用户，我希望能够在当前标签页本次访问中关闭公告栏，以便减少已知信息的重复展示。
8. 作为用户，我希望关闭公告栏后仍能从列表查看公告，以便需要时重新阅读。
9. 作为用户，我希望新公告发布后仍能获得提示，以便关闭过旧公告不会让我错过新信息。
10. 作为用户，我希望公告到期或撤下后停止展示，以便不会继续依据失效信息行动。
11. 作为已经打开公告详情的用户，我希望公告失效后页面提示失效并停止展示正文，以便及时知道信息已经不再有效。
12. 作为用户，我希望公告无需强制签收或自动弹窗，以便正常操作不会被打断。
13. 作为管理员，我希望保存和修改公告草稿，以便发布前准备准确内容。
14. 作为管理员，我希望明确选择公开公告或站内公告，以便控制内容面向的访问者。
15. 作为管理员，我希望确认后立即发布公告，以便及时传递信息。
16. 作为管理员，我希望可以设置公告到期时间，以便过期信息停止对用户展示。
17. 作为管理员，我希望可以主动撤下已发布公告，以便取消维护或修正错误信息。
18. 作为管理员，我希望通过撤下旧公告、发布新公告来更正内容，以便保留历史事实并让用户看到新信息。
19. 作为管理员，我希望查看草稿、有效、到期和撤下的公告记录，以便管理历史内容。
20. 作为管理员，我希望手动向指定启用用户发送通知，以便传递只与这些用户相关的消息。
21. 作为管理员，我希望向发布时所有启用用户发送通知，以便完成一次明确受众的群发。
22. 作为管理员，我希望指定接收人失效时整次发送失败，以便不会误以为所有目标用户已收到消息。
23. 作为管理员，我希望继续查看手动通知发布记录、接收人数和汇总已读人数，以便了解发送结果。
24. 作为普通用户，我希望只能读取和标记自己的通知，以便个人消息不会泄露或被他人操作。
25. 作为用户，我希望铃铛显示未读数和最近通知，并能打开分页通知列表，以便快速了解和查找消息。
26. 作为用户，我希望列表与预览不会自动将通知标为已读，以便未实际阅读的消息仍有提醒。
27. 作为用户，我希望打开通知详情后标记已读，并可以执行全部已读，以便管理个人阅读状态。
28. 作为同时使用多个页面的用户，我希望一处已读操作实时同步到其他页面，以便各处未读数保持一致。
29. 作为在线用户，我希望新通知在正常网络下及时更新页面，以便无需等待固定刷新周期。
30. 作为在线用户，我希望仅获得焦点且可见的页面给出一次轻提示，其他页面静默更新，以便减少多标签页打扰。
31. 作为离线后返回的用户，我希望重连后看到完整通知和正确未读数，以便不会遗漏持久化消息。
32. 作为离线后返回的用户，我希望离线期间的消息不逐条补弹，以便恢复使用时不会受到集中打扰。
33. 作为用户，我希望连接异常时自动尝试重连，也能手动刷新，以便恢复消息查看。
34. 作为退出登录或会话失效的用户，我希望页面清除个人消息并停止个人实时连接，以便旧身份的消息不会继续显示。
35. 作为用户，我希望退出登录后仍可查看公开公告，以便公开信息不依赖个人会话。
36. 作为收到业务通知的用户，我希望可通过合法站内路径进入相关业务页面，以便继续处理消息关联的事项。
37. 作为账号重新启用的用户，我希望已有个人通知仍保留，以便继续查看历史；禁用期间的全体通知不补发。
38. 作为后端业务开发者，我希望通过明确的发送入口传入接收人、标题、正文和可选站内路径，以便项目接入通知时无需调用通知 HTTP 接口。
39. 作为后端业务开发者，我希望业务操作、通知和审计共同成功或回滚，以便业务成功响应具有可信的通知记录。
40. 作为后端业务开发者，我希望提交后的实时推送失败不会撤销已经成功的业务，以便连接故障不破坏持久化结果。
41. 作为管理员和用户，我希望只有实际角色集合变化才产生角色变更通知，以便重复保存不会产生无效消息。
42. 作为脚手架使用者，我希望单 API 实例可复用现有 PostgreSQL 或 SQLite，无需安装 Redis 或 MQ，以便以较少依赖部署通知功能。
43. 作为部署维护者，我希望获得 SSE 的代理缓冲、连接超时与验证说明，以便部署后仍能保持流式更新。
44. 作为项目维护者，我希望有明确的容量验证记录，以便判断本项目的规模是否需要进一步验证或扩展。

## Implementation Decisions

- 沿用领域词汇表中的公开公告、站内公告、站内通知、全体用户通知、通知已读、角色变更通知和公告撤下；公告与个人接收记录具有不同生命周期，不能只扩展现有全体用户发送开关来表达公告。
- 扩展公告管理与查询、站内通知、用户角色变更、认证会话、应用组装及前端公共布局、登录页和消息页面。继续使用模块化单体，不新建独立消息服务。
- 新增公告持久化及必要的通知跳转元数据。公告保存标题、纯文本正文、公开或站内范围、草稿或发布或撤下状态、发布时间及可选到期时间；是否当前有效结合状态与时间判断。管理历史保留，不自动清理。
- 公告草稿可编辑；已发布公告内容和可见范围固定。更正采用撤下旧公告并发布新公告；不通过将已发布站内内容改为公开来改变信息边界。
- ADMIN 独立拥有公告与手动通知管理权限，服务端负责授权。普通用户只查询有效可见公告及自己的通知。匿名接口及匿名流不得返回草稿、撤下或到期公告、站内公告、个人消息、接收人或管理信息。
- 公告无逐人接收记录、已读统计或确认签收。关闭公告栏仅作用于当前标签页本次访问；列表仍可查询有效公告，新公告继续提示。
- 个人通知沿用发布时启用且未删除账号快照、指定接收人整体校验、内容发布后固定、历史保留、详情已读、全部已读和管理员发送统计。发布后新增账号不补收历史全体通知，禁用期间的全体通知不补发。
- 管理接口提供公告草稿创建与修改、立即发布、主动撤下及历史查询；公开与登录查询提供有效公告列表和详情；个人通知查询、未读与已读沿用既有兼容契约。新增和变更接口同步 Swagger 或契约文档，保持统一响应、错误和分页约定。
- 统一后端业务发送入口接受接收用户、标题、纯文本正文和可选站内跳转路径，业务模块无需调用通知 HTTP 接口。事务写入留在持久化边界，不向业务 Service 暴露 Gin 或 GORM 类型。
- 角色变更经统一入口接入，实际角色集合变化才发送，包括首次分配、调整和清空；重复保存相同集合不发送。通知内容保留变更前后角色，新建账号本身、修改角色定义和角色菜单不触发通知。
- 延续 ADR-0007：角色变更、操作审计和通知同一事务提交，手动群发同样整体成功或回滚。事务拥有方在提交成功后广播，事务内部的通知写入不直接推送；仅在管理员发送方法后推送不足以覆盖业务自动通知。
- 采用 ADR-0012 的 SSE 边界：持久化状态为事实来源，流推送变化提示，REST 返回完整状态；不持久化逐条重放实时事件，不补弹离线通知。实时推送失败不会使已提交业务变成失败。
- 提供隔离的匿名公开流与登录流；公开流传递公开公告变化，登录流传递该用户可见的站内公告、通知及阅读状态变化。所有已登录页面更新列表和未读数，只有获得焦点且可见的页面给轻提示；不做跨设备提示去重。
- 沿用 Authorization Bearer 鉴权，前端使用 fetch 流式读取 SSE，管理连接、重连和取消；不把登录 token 放进 URL，不更改既有认证契约。允许心跳、认证有效性检查与断线重试，不定时查询消息或提供轮询降级。
- 连接建立时鉴权之外，发送个人事件前确认会话有效；JWT 到期关闭连接，心跳检查会话撤销。登录态变化中止旧连接并清除个人消息，账号禁用、登出或会话失效后停止个人事件，公开公告能力仍可用。
- 初次同步与重连先建立订阅再获取状态，并处理同步期间变化，避免快照与订阅之间漏更新。读取失败允许有界重试及手动刷新，不启动定时消息查询。重复事件、连续变化和慢连接不能导致无限队列或重复提示。
- 公告发布、撤下和到期更新相关页面；服务端安排到期变化通知，客户端按到期时间停止展示，查询接口始终检查有效性。已打开的详情失效后停止展示正文，重启后恢复到期安排。
- 可选跳转只接受本系统路径，拒绝外部地址及脚本协议，目标页继续校验业务权限。未设置路径时打开通知详情；跳转不绕过详情已读规则，列表预览仍不算已读。
- 管理成功写操作继续写入事务内审计。PostgreSQL 与 SQLite 增加对应版本化迁移并维持逻辑版本锁步，保留真实数据库契约验证，不由 API 自动迁移。
- 首版承诺单 API 实例，无 Redis 或 MQ。容量验证基线为 100 条并发 SSE 连接、最多 1,000 个启用账号的全体通知；匿名、多标签页、多设备和同时建立的两类流分别计入连接数。正常网络下发布成功后 2 秒内更新在线页面；基线不是产品硬上限或任意规模性能承诺。
- 不自动弹窗、不播放声音、不发送浏览器桌面通知。开发和部署说明包含 SSE 流式响应、反向代理缓冲、连接超时及连接清理。

## Testing Decisions

- 用户已确认测试边界：优先通过现有 HTTP 集成契约入口验证 REST、SSE、权限、已读和恢复；角色变更经真实业务操作入口验证；前端验证用户可见行为，不断言内部组件、函数调用次数或具体队列实现。
- 复用真实 migration、隔离数据库及完整应用路由构建的 PostgreSQL 通知 HTTP 契约和 SQLite 共享 HTTP 业务契约。现有契约可作为基础，但不能假设已完整覆盖通知失败回滚、快照受众或重复角色；补齐本规格行为。
- SSE 使用真实 HTTP 测试服务器与流式客户端，在同一应用边界验证长连接、事件与后续查询结果；普通收集完整响应的测试 recorder 不适合作为无限事件流的客户端。使用可控超时和清理，避免挂住测试。
- 数据库与 HTTP 验证公告草稿、发布、到期、撤下、失效详情、管理员历史及匿名隔离；验证新用户可看有效公告但不能补收历史全体通知，指定收件人失效时整体失败及不同用户的通知、已读隔离。
- 通过角色分配和管理员发送的公开行为验证事务：业务或审计或通知持久化失败时全部回滚，且没有实时事件；提交后广播失败时业务仍成功，查询和重连可恢复消息。复用既有业务与审计事务回滚测试的数据库失败注入方式，不新增面向测试的公共业务接口。
- 阅读测试覆盖预览不已读、详情已读、全部已读、重复已读不重复累计、管理员统计及同用户多页面同步。角色测试覆盖首次分配、调整、清空与相同集合重复保存不发送。
- 实时测试覆盖匿名与登录流隔离、在线到达、公告撤下与到期、跨页面阅读同步、断线及服务重启恢复、订阅与快照交界期间变更、慢连接和重复变化；断线期间消息不补弹，正常运行与故障恢复均无消息轮询。
- 鉴权测试覆盖不同用户及匿名越权、退出登录、会话到期、撤销和账号禁用，确认失效身份不再收到个人事件且公开公告仍可访问。跳转测试拒绝外部地址和脚本协议，并验证业务目标页保持授权约束。
- 前端复用已有 Playwright 浏览器行为脚本基础设施，验证登录前后公告展示、关闭公告栏范围、新公告提示、失效详情、通知预览与已读、双标签页焦点提示、登录态变化及合法跳转。可模拟网络验证显示行为，真实 SSE 可靠性由 HTTP 流测试补充。
- 容量测试分别使用 PostgreSQL 与 SQLite，在单实例、100 条并发连接和最多 1,000 个启用账号群发的基线下记录机器配置、数据库类型、网络条件、负载及发布成功至页面状态更新的实测延迟，验证 2 秒目标。浏览器页面更新与协议事件到达分别观测，不能用后者替代前者。
- 实施时执行迁移验证、后端测试与静态检查、PostgreSQL 和 SQLite 集成契约、前端 lint 和构建。长时间运行的验证检查健康和数据库就绪，测试结束关闭连接及进程，测试不得连接实际部署数据库。

## Out of Scope

- 邮件、短信、微信等外部渠道，审批待办的业务状态。
- 角色、部门或复杂条件受众，多租户通知隔离模型。
- 公告预约发布、发布审批、富文本，已发布正文编辑。
- 公告逐人已读统计、强制签收，普通用户查询失效公告历史。
- 用户任意发送、通知个人删除、历史自动清理、已发布通知编辑或撤回。
- 自动弹窗、声音、浏览器桌面通知、跨设备提示去重。
- 模板管理、异步补发队列、独立发送去重平台、逐条实时事件持久化重放。
- 消息轮询及连接失败时轮询降级。
- 多 API 实例的跨实例投递，Redis、MQ 或独立消息服务。
- 超出容量基线的性能承诺，MySQL 正式兼容验证。

## Further Notes

- 本规格基于用户逐轮接受并最终确认的设计，测试边界也已确认，可标记 ready-for-agent，无需再次需求访谈。
- 领域词汇表和 ADR-0007、ADR-0012 为设计依据。首版“站内通知设计”保留历史决策，其中 30 秒轮询由本规格替代，其余明确沿用的通知语义继续有效。
