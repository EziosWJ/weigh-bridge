# 厂区本地确认业务，中心统一资料并汇总

> **2026-10-22 效力：部分被替代，中心能力暂缓。** 本地业务权威、断互联网可运行、编号与快照继续有效；中心管理账号资料／归属及首次下发依赖被替代，双向同步、中心审批与跨厂汇总退出本期。当前依据见 [ADR 0023](0023-standalone-site-baseline.md)及[基线索引](../development-baseline.md)；下文历史正文保留。

2026-10-22，用户确认现场互联网不稳定，外网中断不得阻塞生产。每个厂区独立部署可完成业务闭环的本地系统，由本地 Server 校验操作员确认、保存称重依据并形成正式电子过磅单；Agent 继续负责现场设备。外网断开而本地服务与设备链路正常时，可继续办理；本地确认成功的正式单据不等待中心再次审批或出单。此为已确认的目标架构，尚未实现，不代表真实仪表、摄像头或正式称重已验收。

中心统一维护物料及往来主体，各厂保存可离线使用的资料。有网时自动持续同步，断网后恢复追平；厂区业务及其后续作废、更正等变化上传中心，资料更新下发各厂。中心跨厂查询必须表达数据更新时间，不能把未同步当成没有业务。历史单据保留出单时的资料快照，资料更新不改写历史依据。物料由中心预先建档；普通操作员默认具有独立的临时往来主体补录权限，不开放完整资料维护。中心人工确认转正式或关联已有主体，同名不自动合并，保留历史快照与来源，通过关联统一查询汇总。

这一决定调整 [ADR 0018](0018-site-business-isolation.md) 中“一套 Server 与数据库管理两厂”的部署前提，以及此前远程 Server 架构下“断云暂停正式确认”的规则；厂区业务隔离、同厂两次称重、人工确认、原始依据留存及打印结果核实继续适用。中心同步已经在本地确认的业务，不自动补办历史称重，不重新出单或触发打印。本地 Server／数据库或 Agent 链路故障不等于互联网中断，仍按对应故障规则处理。

用户在第一轮 Q1～Q6 回复“接受建议”：中心与厂区复用当前 Server／Web 代码，按角色启用功能，分别部署并使用独立数据库，由后端约束职责；账号、岗位权限及厂区授权由中心统一维护，厂区独立登录鉴权；中心接收任务、称重记录、各版单据、业务审计、打印尝试及对应抓拍，业务数据优先、图片随后补齐且分别标明完整性。首期中心只查询汇总及管理资料，不发起作废、更正、重开或打印，不建设断网后自动补执行的远程业务指令队列。

中心统一管理厂区、地磅及 Agent 归属和连接身份，现场明确应用；本机串口、摄像头、打印队列及校准参数仍由现场维护。同一目标阶段交付本地独立办理、统一资料与双厂自动同步闭环，先验证本地再验证同步；真实仪表、摄像头按原计划单独接入验收。

第二轮 Q7～Q12 已确认：厂区离线使用最近同步的账号权限，可本地重新登录，会话仍正常过期，不因离线天数停产。账号授权及密码修改／重置统一在中心办理，厂区收到更新后生效，适用时撤销旧会话，不撤销已提交业务；因此中心撤权无法在断网厂区即时生效。厂区收到基础资料停用更新后禁止新任务选用，已开始任务可沿用原依据正常回磅。中心提出厂区停用意图，现场满足既有停用条件并明确应用后才算生效，未确认显示待现场处理。

正常网络、无积压时，业务和资料变更以 1 分钟内同步可见为验收目标；图片单独标记完整性，积压恢复显示进度，不因上传等待阻塞现场确认。

第三轮 Q13～Q19 中，用户明确 Q15 部署在各厂工控机，其余接受建议：每厂预先同步至少两名实名授权人员，离线忘记密码时由另一人以本人账号接班；临时主体可在本厂等待确认期间重复选用，中心确认后再分发其他厂；新单号包含稳定厂区码且重装恢复不得复用已用编号；原联调数据备份封存，新生产任务与单据从空库开始，仅迁入确认资料、账号授权和现场身份，保留 Agent 打印账本；首次联网初始化后验证脱网办理。

用户接受单块业务盘损坏时保护已确认业务与抓拍的目标，但随后明确“现阶段先不讨论单盘故障保护方案了，先说清楚业务修改”。该目标保留，具体保护方案、硬件投入与恢复指标暂缓讨论，不作为当前业务访谈的阻塞，也不能宣称已经实现或验收。

第四轮 Q20～Q23 已确认：厂区端固定本厂工作台、业务、查询和统计，管理人员按授权在中心跨厂查询；临时主体收到退回补充结果后禁止新任务选用，既有任务续办，补充再次提交后待中心确认恢复；已首磅任务沿用原资料快照，中心修改物料规格、主体名称或业务身份用于新任务，主动纠正按既有流程留痕；中心完整业务数据已到达的有效单据正常计入汇总，图片未齐另行标记，不作为单据无效的依据。

选择本地业务权威会增加同步、独立编号、资料分发及本地备份恢复的成本，但消除正式称重对互联网的实时依赖。独立中心项目会重复维护认证、业务模型和审计，当前选择同一项目内按角色装配，避免两套规则分化。Q1～Q23 业务规则逐轮确认后，用户对[业务修改规格](../requirements/local-first-deployment-spec.md)回复“确认”，完成汇总最终核对，本轮业务访谈结束，作为后续技术设计依据；详细过程见[需求访谈](../requirements/local-first-deployment-discovery.md)。此决定不构成开发、部署、提交或推送授权。

用户随后调用 `to-spec`，确认测试以既有 HTTP API 为主要边界、中心与两厂实例及 Agent mock 驱动，辅以少量浏览器冒烟。规格已发布为 [EziosWJ/weigh-bridge Issue #4](https://github.com/EziosWJ/weigh-bridge/issues/4)，标签 `ready-for-agent`；尚未启动本地部署角色或同步功能实现。
