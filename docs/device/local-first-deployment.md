# 中心与厂区独立部署

对应 [Issue #4](https://github.com/EziosWJ/weigh-bridge/issues/4)。本说明不表示已切换现有工控机。每厂目标为本机 Web、Server、PostgreSQL、Agent；SQLite 保留开发和兼容测试用途。

## 部署准备

- 核验两厂工控机磁盘容量、内存、CPU、PostgreSQL/Server/Agent 共存及开机恢复；明确本厂 LAN 地址、中心 HTTPS 地址和时间同步来源。
- 停止联调写入后，原数据库、图片、忽略的配置原样封存。PostgreSQL 使用一致 `pg_dump`；SQLite 可使用现有 `task db:backup`。同时封存 Agent 配置和打印账本，不删除旧浏览器演示库。备份含凭据，存储访问权限按现场维护约定处理。
- 新中心与两个生产厂区分别建空库，显式执行 `task db:migrate`。不将旧联调任务或单据当作生产数据导入。仅迁入人工确认的正式资料、实名账号授权、厂区及 Agent 身份；保留现场打印账本。
- 使用 `task build` 发布构建，把 Web 和 Server 安装在各工控机，不依赖外网托管页面或字体。数据库监听范围与备份策略按现场既有运维安排。

## 实例配置

参考 [节点配置示例](../../server/configs/config.node.example.yaml)，写入被忽略的本地 `server/configs/config.prod.yaml` 或环境变量。中心 `node.role: central` 并配置两个独立 peer；厂区使用 `node.role: site`、稳定 `site_id`、`central_url` 和对应 `sync_key`。支持 `APP_NODE__ROLE`、`APP_NODE__SITE_ID`、`APP_NODE__CENTRAL_URL`、`APP_NODE__SYNC_KEY`，中心 peer 列表支持 `APP_NODE__PEERS` JSON。

三个实例使用独立 PostgreSQL 数据库、JWT 密钥、上传目录及 `weighing.image_dir`。节点身份一经写入数据库不能通过改配置切换；启动不执行建表。保留空角色的旧配置仅用于开发联调，不能用来替代生产厂区角色。

中心后台先配置正式资料、两厂和地磅，分别填写“本厂 Server 地址”，保留原 Agent 编号。每厂至少授权两名具备称重确认权限的实名操作员。保存已有厂区配置会形成“待现场应用”提案。厂区首次同步账号资料后，维护人员在本厂“厂区配置”明确应用提案，再从本厂下载 Agent 启动配置导入本地维护服务。Agent 的连接地址应为该厂工控机地址，不能使用中心地址。原打印参数与账本保留，按既有导入应用流程启动现场 Agent。

## 启用验证与回退

1. 检查三个实例的 `/health`、`/ready`；核对本厂能力列表仅出现本厂，中心不存在现场称重或打印操作入口。
2. 分别以两名实名操作员验证本地登录；首轮下发未满足人数和动作权限时，生产写入仍被禁止。密码修改/重置从中心办理。
3. 只断开工控机到中心的互联网链路，保留本地浏览器、Server、数据库及 Agent 链路。刷新页面、重新登录、按人工核对流程办理、查询和核实打印。
4. 恢复中心链路，观察业务和资料在正常无积压时 1 分钟内可见，积压逐步减少；中心有效单据统计不等待图片，图片随后补齐。确认历史单据和打印次数未变化。
5. 中心提出停用后，仍显示待现场应用；现场结束任务、核实打印、停止 Agent，再明确应用并同步回执。不得将中心连接过期当成现场已经停用。
6. 回退时先停止新生产写入并保存已经确认的生产库和图片，再按实际已应用的 schema 与二进制版本恢复。不得直接用联调备份覆盖新生产交易；旧备份恢复前校准时钟并核对与中心差异。

本次没有替用户执行真实生产数据迁移、实物打印或工控机切换。单盘故障保护、恢复指标及演练仍按用户要求暂缓，不能由软件测试结果替代。
