## 本轮诉求

用户提出补充厂区配置页面，以及 Agent 对应厂区的启动配置。现有多厂区业务隔离和用户厂区授权继续沿用，新增配置能力的具体范围逐轮确认。

## 已核对的现状

- “称重作业 → 厂区工作台”用于查看授权厂区、地磅及 Agent 状态、进入称重台，不提供厂区资料维护。
- “用户管理 → 厂区”用于分配查询及操作范围，不维护厂区或 Agent 身份。
- 初始厂区与地磅由数据库迁移和种子数据建立；现有厂区 API 提供查询和用户授权，没有厂区新增、编辑接口。
- 地磅归属于厂区；Agent 通过地磅映射确定现场归属。目前每厂一磅，厂区、地磅与 Agent 分别保留身份。
- Server 当前从受保护的配置读取 Agent 编号、地磅 ID 与密钥映射，修改列表后需重启；现场 Agent 还需配置对应身份、服务地址及本机打印参数。
- 真实打印 Agent 的本地维护台已可手填上述连接身份及打印参数，尚无厂区名称选择或后台配置导入流程。保存草稿不影响运行；明确应用会核对未结束作业、停止 Agent、写入 `agent.env` 并启动核实，失败恢复原配置。Agent 启动时读取配置，不支持运行中热更新；本轮应复用既有维护能力。
- 同磅真实 Agent 与 mock 互斥、踢出与未决打印规则沿用已确认需求。仪表和摄像头尚未接入，不能将配置能力描述为设备驱动已完成。

## 第一轮已确认（Q1～Q3）

用户回复“接受建议”，确认以下范围：

- Q1：支持厂区新增、编辑和停用，一并维护对应地磅。本期每厂一台地磅，不提供物理删除，保留历史记录。
- Q2：后台选定厂区和地磅生成专用启动配置，现场维护人员应用配置并启动。复用既有本地维护台，明确展示厂区和地磅；本轮不采用后台远程启动现场进程。
- Q3：真实打印 Agent 和 mock 都覆盖对应厂区的启动配置，继续遵守同磅单 Agent 在线规则。

以上为第一轮确认范围；后续规则见以下各轮结论，实际实施与部署结果以交付记录为准。

## 第二轮已确认（Q4～Q8）

用户再次回复“接受建议”，确认以下规则：

- Q4：新增“厂区配置”和“启动配置导出”独立权限，默认仅管理员拥有。用户业务查询、操作范围仍在用户管理中单独授权，不能由配置权限替代。
- Q5：后台保存 Agent 绑定后，新连接即可使用，不再要求手工修改服务端配置或重启 API。现场 Agent 仍需明确应用配置并启动。
- Q6：存在未完成任务、未决打印或在线 Agent 时阻止停用，明确列出原因。停用后禁止新业务及设备接入，保留历史查询和导出；允许重新启用。不能继续使用当前只查询启用厂区的逻辑隐藏停用厂区历史。
- Q7：已有地磅和 Agent 身份不跨厂改绑。硬件搬迁通过目标厂区的新身份表达，原历史及打印账本保留。
- Q8：后台生成配置仅覆盖 Server 地址、厂区／地磅信息及 Agent 连接凭据；本地导入先预览，再明确应用，保留 CUPS 队列、校准参数和打印账本。mock 使用对应配置文件启动。

上述规则已按后续结论实施。后台配置成为 Agent 绑定的管理来源，现场明确应用仍为进程配置生效边界，见 [ADR 0020](../adr/0020-managed-agent-bindings-and-local-activation.md)。

## 第三轮修订结论（Q9、Q10）

用户明确要求简化 Q9、Q10：系统部署于厂区内部，本轮只需让 Agent 启动时区分对应厂区，不因假冒或伪造的假设增加安全流程。

- 启动配置作为可重复下载、保存和使用的普通配置文件；导出同一厂区配置不使已下载文件失效，不要求先重置凭据。
- 不引入一次性签发、凭据轮换流程，撤回本轮所提“离线且无未决打印才允许重置”的新增要求。
- 沿用现有 Agent 连接机制，配置自动携带连接所需参数；操作人员只需确认厂区和地磅，真实 Agent 本地导入应用，mock 读取对应文件启动。
- 现有同磅 Agent 互斥、现场应用配置时的打印作业核查及厂区停用规则继续按已确认范围执行，不把这些检查扩展到普通配置下载。

旧配置迁入保留现有身份、密钥和账本，不因升级自动重置；后台管理启用后旧文件不得反复覆盖后台修改。具体迁入与验证步骤纳入实施方案。

## 第三轮最终确认（Q11）

- 用户在具体示例解释后回复“可以”，确认后台统一设置工控机可访问的 Server 地址；下载各厂区的启动配置时自动包含该地址，无需现场逐项重复填写。
- 导出内容同时包含选定厂区、地磅和对应 Agent 的连接信息。示例地址仅用于说明，不作为实际部署默认地址。
- 修改后台地址不会直接改写工控机当前运行配置；需要现场导入并明确应用更新后的文件，继续遵守 Q2、Q8 的生效边界。

本轮无剩余待决业务问题。用户随后明确启动实施并要求部署 Agent 到 `fcc-com-01`。以下保留确认范围与验收预期，准确实现、验证与现场结果见[交付记录](site-agent-configuration-delivery.md)。

## 完整操作流程

1. 管理员在后台厂区配置页面新增或编辑厂区及其唯一地磅，管理对应 Agent 绑定；沿用既有编号时保留现有业务及连接身份。
2. 管理员统一设置工控机可访问的 Server 地址，选择厂区下载启动配置。文件可重复下载及使用，普通下载不影响在线 Agent 或既有文件。
3. 真实打印 Agent：在本地维护台导入配置，预览厂区、地磅和连接信息，保留本机打印队列及校准设置；明确应用后按既有现场作业核查流程启动。
4. mock：读取对应厂区的启动配置启动，可独立指定控制端口；不同厂区可同时运行，地磅归属由配置明确指定，不静默选择其他厂区。
5. 用户在用户管理中获得业务厂区查询或操作授权，再从厂区工作台进入相应现场。配置维护权限与业务授权分别管理。
6. 停用厂区前核查未完成任务、未决打印和在线 Agent；任一条件存在则列明原因并阻止停用。停用保留历史查询及导出，重新启用后恢复按授权办理业务。

后台保存绑定仅对之后的新连接生效，不静默切换已建立连接的厂区归属；已有连接继续使用原归属，仍受既有同磅互斥和踢出规则约束。

## 实现约束与验收条件

| 场景 | 验收预期 |
| --- | --- |
| 厂区资料维护 | 有权限人员可新增、编辑、停用和重新启用厂区，本期每厂一磅，无物理删除入口 |
| 权限 | 厂区配置与启动配置导出使用独立动作权限，默认仅管理员拥有；普通操作员继续按既有业务权限及厂区授权办理 |
| 新厂接入 | 后台保存绑定后即可接受对应新连接，无需修改 Server 文件或重启 API |
| 启动配置 | 包含后台填写的 Server 地址及指定厂区、地磅、Agent 连接信息，可重复下载；不要求一次性签发或凭据轮换 |
| 真实 Agent 导入 | 先预览再明确应用；保留本机 CUPS 队列、校准参数和账本，应用失败继续按既有恢复机制处理 |
| 首次现场配置 | 新工控机仍在本地维护台选择本机队列、检查打印参数，再明确应用；后台连接配置不伪造本机已有打印设置 |
| mock 启动 | 可直接读取对应现场配置，并使用独立控制端口同时运行两个厂区实例；启动及状态展示可核对归属 |
| 同磅互斥 | 真实 Agent 与 mock 同磅并发时保留已在线者，后来者明确冲突；不同厂区互不影响 |
| 地址与绑定更新 | 后台保存不直接修改现场文件或切换在线连接归属，现场明确应用后重新接入 |
| 停用条件 | 未完成任务、未决打印或在线 Agent 任一存在即阻止，并列出原因；无阻塞后允许停用 |
| 停用后的行为 | 阻止新业务及设备接入；已有业务历史可按原授权查询和导出，允许重新启用 |
| 归属与搬迁 | 已有地磅和 Agent 身份不跨厂改绑；搬迁使用目标厂区新身份，原历史和账本保留 |
| 旧配置迁入 | 保留有效身份、密钥、业务历史和打印账本，迁入后旧文件不反复覆盖后台配置；普通升级不使已有现场配置失效 |
| 现有业务回归 | 厂区隔离、用户授权、任务办理、单据历史及打印结果核实语义保持，既有单据内容不因改厂区名称而改写 |
| 数据库与检查 | 结构变化新增 Goose migration，兼容 PostgreSQL 和 SQLite；按改动运行后端检查、前端 lint/build 及数据库相关检查，并覆盖两厂启动和停用历史查询的核心行为 |
| 真实设备边界 | 本轮交付配置与启动能力，不将其描述为仪表、摄像头驱动或真实称重设备验收完成 |
