# 独立称重工作台、专用车牌录入与模拟识别 Spec

后续业务修订（2026-10-18，已确认、待实现）：操作员处置、双向人工重量调整及出单后单磅重称以 [补充 Spec](operator-weighing-corrections-spec.md) 为准。下文主管权限及“保持原重称与调整规则”的描述是本次独立工作台已交付基线，不限制后续业务修订；现有识别及独立页面交付事实保持原样。

状态：2026-10-18，用户已启动 Issue #2 实施，已完成前端模拟扩展；范围与验收决策保留如下，实际结果见 [交付记录](standalone-workbench-delivery.md)。测试以浏览器流程为主，保留既有核心回归。真实识别与正式称重业务仍未实现。

已发布：[EziosWJ/weigh-bridge Issue #2](https://github.com/EziosWJ/weigh-bridge/issues/2)，标签 `ready-for-agent`。

## Problem Statement

磅房操作员需要长期停留在称重工作台，连续办理车辆。当前工作台位于后台布局内，侧栏、通用顶栏和管理页面的排版约束占据现场观察及操作空间，查询或维护资料也会打断当前车辆办理。

车牌目前通过一个普通输入框手填，没有省份简称选择、专用号牌呈现或模拟识别过程。操作员无法验证日后正常作业中“摄像头给出候选车牌，人工看图核对或修正，然后匹配运输任务”的完整体验。

仅将当前页面放到另一个标签页不能解决上述问题：现有页面仍依赖后台外壳，称重模拟状态也尚无跨标签实时同步。需要让独立工作台与后台协作时保留当前草稿及有效采集，避免旧页面的状态覆盖另一页已经保存的业务数据。

## Solution

提供供磅房长期值守的独立称重工作台。操作员点击后台菜单，在浏览器新标签打开；重复点击回到已经打开的工作台。工作台沿用已有登录，脱离后台侧栏、面包屑、公告和通用顶栏，保留自己的紧凑操作栏、必要状态、后台入口及全屏按钮。

使用 frontend-design 设计适合人工操作的页面：左侧约六成为现场观察区域，右侧集中重量、本趟必要资料与当前主操作。现场画面可调大小、可放大；日常办理时关键画面、资料和按钮应处于常用桌面首屏。完整查询、资料维护和演示设置放在后台标签，工作台保持当前车辆。

以专用车牌控件替代业务录入和修改中的普通输入框。省份简称通过网格选择，后续字符分格显示，同时支持连续键盘输入、完整车牌粘贴和自动转大写，覆盖普通与新能源车牌。

模拟流程为：模拟车辆到磅 → 模拟识别产生候选或失败 → 操作员对照模拟车牌特写核对或修改 → 点击“核对车牌并查找运输” → 采集重量及抓拍 → 补齐资料 → 一次集中核对 → 明确确认保存。首磅确认才建立运输任务，回磅确认同时完成任务并生成测试单据。

演示设置配置模拟现场车牌、识别候选及正确／错误／失败场景。场景提供可直接体验的默认值，也允许自行设置，以便用同一车牌演示首磅和回磅。所有识别、画面、抓拍和单据继续明确标记模拟或测试。

## User Stories

1. 作为操作员，我希望点击后台称重菜单就能在浏览器新标签打开独立工作台，以便将称重作业作为长期使用的工作页面。
2. 作为操作员，我希望重复点击菜单时回到原工作台，以便快速找到正在办理的车辆。
3. 作为操作员，我希望工作台有可以直接访问的地址并沿用已有登录，以便重新打开时不必寻找后台层层入口。
4. 作为操作员，我希望工作台没有后台侧栏、面包屑、公告和通用顶栏，以便把空间留给车辆观察与称重。
5. 作为操作员，我希望紧凑操作栏显示当前身份、必要状态、后台入口和全屏按钮，以便明确所处环境并控制显示方式。
6. 作为操作员，我希望自行进入或退出全屏，以便按现场屏幕和工作习惯切换。
7. 作为操作员，我希望在工作台左侧清楚看到车辆画面，以便观察车辆是否完全上磅。
8. 作为操作员，我希望调整画面大小及放大查看，以便核对车辆位置和车牌细节。
9. 作为操作员，我希望放大或缩小画面不会改变已采集重量，以便安心调整观察视野。
10. 作为操作员，我希望重量、稳定状态和主操作清晰醒目，以便快速判断下一步。
11. 作为操作员，我希望常用桌面首屏同时显示关键画面、必要资料和主操作，以便减少上下滚动。
12. 作为操作员，我希望小屏下内容正常堆叠且控件可用，以便在较窄窗口中继续操作。
13. 作为操作员，我希望车牌输入先选择晋、京、苏、沪等省份简称，以便减少重复输入和录入错误。
14. 作为操作员，我希望后续车牌字符分格显示但能连续键盘输入，以便既容易辨认又不必逐格点击。
15. 作为操作员，我希望粘贴完整车牌时自动拆分省份与后续字符，以便快速录入已有号码。
16. 作为操作员，我希望输入的小写字母自动转为大写，以便保持车牌表达一致。
17. 作为操作员，我希望普通和新能源车牌都能正确输入和展示，以便办理不同车辆。
18. 作为操作员，我希望格式有误时得到明确的修正提示，以便在查找任务前纠正输入。
19. 作为操作员，我希望点击“模拟车辆到磅”后看到识别过程及结果，以便提前体验真实设备接入后的作业顺序。
20. 作为操作员，我希望模拟画面中有清晰的现场车牌特写，以便真正对照候选结果进行人工核对。
21. 作为操作员，我希望正确识别的候选自动填入车牌控件，以便核对后快速办理。
22. 作为操作员，我希望识别出错时能直接修改省份或后续字符，以便修正结果后继续原流程。
23. 作为操作员，我希望识别失败时仍能使用同一个专用控件人工录入，以便继续模拟办理。
24. 作为操作员，我希望识别候选明确处于待核对状态，以便区分机器候选与已经人工认可的车牌。
25. 作为操作员，我希望一次点击“核对车牌并查找运输”完成车牌认可与任务定位，以便避免重复确认按钮。
26. 作为操作员，我希望未人工核对的候选不会直接绑定运输任务或用于称重确认，以便避免车辆错配。
27. 作为操作员，我希望正在修改车牌、核对或称重时新候选只作提示，以便当前工作不被覆盖。
28. 作为操作员，我希望明确办理下一辆后再接入下一辆候选，以便连续作业时保持车辆边界清楚。
29. 作为操作员，我希望车牌定位后系统明确提示首磅或回磅，以便进入正确的运输环节。
30. 作为操作员，我希望车辆上磅后先采集重量与抓拍，再补齐物料和供收方，以便适应现场操作顺序。
31. 作为操作员，我希望只采集但未最终确认时不会生成运输任务或单据，以便分清采集和业务提交。
32. 作为操作员，我希望同车补资料保留有效的重量、抓拍和采集时间，以便避免无意义的重复采集。
33. 作为操作员，我希望定位后修改车牌会要求重新查找并清除旧采集，以便避免将上一车的依据用于另一车。
34. 作为操作员，我希望在一个窗口对照车牌、业务、重量和抓拍并明确确认，以便集中核对整次称重。
35. 作为操作员，我希望回磅时同时看到首次依据、原始重量和最终重量输入，以便正确办理两方向称重及人工扣减。
36. 作为操作员，我希望固定确认区持续显示最终毛皮净重及确认按钮，以便调整后准确出单。
37. 作为操作员，我希望称重成功后看到结果、任务或单据入口以及办理下一辆按钮，以便明确本次是否完成。
38. 作为操作员，我希望提交结果不明时先查询原结果，以便避免重复建立任务或重复出单。
39. 作为操作员，我希望在后台查询、维护资料或调整演示设置时工作台保持当前车辆，以便办理不中断。
40. 作为操作员，我希望后台新增物料或往来主体后自动出现在工作台候选中，以便补录资料后直接继续。
41. 作为操作员，我希望打开后台或同步资料本身不会清除草稿及有效采集，以便不因页面切换损失进度。
42. 作为操作员，我希望后台实际修改当前任务或现场模拟条件时得到重新核对或采集的提示，以便不用过期数据提交。
43. 作为操作员，我希望两个标签的操作不会用旧状态覆盖已经保存的数据，以便独立工作台和后台可以协作。
44. 作为演示使用者，我希望在独立设置页配置模拟现场车牌、识别候选及结果场景，以便可重复演示识别正确、错误和失败。
45. 作为演示使用者，我希望预置示例可直接体验，也能设置同一车牌完成首磅及回磅，以便验证完整业务闭环。
46. 作为操作员，我希望工作台只保留必要的模拟触发入口，以便配置项不挤占日常操作区域。
47. 作为主管，我希望称重详情保留当次原候选、人工确认车牌和录入来源，以便解释人工修正及任务匹配依据。
48. 作为主管，我希望首磅和回磅分别保留各次识别与人工核对依据，以便后续修改模拟设置不改变历史。
49. 作为主管，我希望任务纠错和单据更正重开也使用专用车牌控件，以便各处的车牌编辑方式一致。
50. 作为主管，我希望已确认后的车牌纠错继续遵守现有权限、原因和留痕规则，以便专用控件不改变业务授权。
51. 作为操作员，我希望确认前修正识别错误不额外要求填写原因，以便日常人工核对保持简洁。
52. 作为查询人员，我希望车牌或编号查询继续支持自由输入，以便搜索部分车牌、任务号和单号。
53. 作为查询人员，我希望已有测试任务、单据和图片保持可查，以便升级页面后不丢历史。
54. 作为查询人员，我希望旧记录缺少识别来源时如实显示未记录，以便不把新模拟结果反填成历史事实。
55. 作为演示使用者，我希望画面、车牌特写、识别结果和单据明确标记模拟或测试，以便正确理解当前交付能力。

## Implementation Decisions

- **阶段与业务边界**：本轮扩展已有 Phase 2A 前端模拟，新增独立页面、专用控件、模拟识别及同源标签协作；不新增称重业务 API、业务表或正式记录。沿用正式称重必须经人工确认、真实设备证据和 Server 校验的领域约束，以及原始／最终重量分别保留的既有决策。
- **工作台外壳与入口**：在已有路由体系内为工作台提供独立页面外壳，保留鉴权。菜单及菜单搜索等同义入口使用一致的打开策略；重复点击复用可用工作台，关闭后可重新打开。原工作台地址和既有携带任务定位的入口仍可到达对应独立工作台，不维护两个分叉的称重办理版本。浏览器新标签由用户点击触发；不能静默打开时提供明确的直接打开入口。
- **后台职责**：完整任务／单据查询、资料维护和演示设置继续使用后台页面；工作台不因这些操作跳走。本次集中核对、称重结果保留在工作台，打印预览另开标签。保留回到后台的清晰入口。
- **视觉设计**：实施时使用 frontend-design，先形成精简的颜色、字体、布局与操作原则，再结合截图自检。工作台允许采用独立于后台的业务布局及局部视觉规则，其他后台页面沿用已有 Pattern。以浅色资料区、左侧约六成现场观察区域和右侧重量操作区为起点，具体比例服从摄像头大小调整及响应式需求。复用成熟控件，不为此新建通用页面框架。
- **尺寸与交互**：常规桌面以 1366×768 为最低既有验证基准，独立页面不再预留后台侧栏宽度；关键画面、必要资料和主操作无需整页滚动。长补充资料与窄屏允许正常滚动。画面保留小窗／标准／大窗和独立放大能力，完整呈现车辆，调整尺寸不影响采集；支持可见键盘焦点、弹窗焦点恢复及正常窄屏堆叠。全屏由操作员主动触发。
- **专用车牌控件**：统一覆盖工作台新录入、识别结果修改、主管任务纠错和单据更正重开；省份简称网格与后续字符组成一个逻辑车牌值。字符分格属于呈现，不要求逐格点选；支持连续输入、完整号码粘贴拆分及转大写。按普通／新能源车牌提供必要的格式提示，不做真实登记状态核验。查询条件不替换为严格号牌控件。
- **识别与确认分离**：明确区分模拟现场车牌、原始识别候选、当前编辑值和人工核对后用于匹配的车牌。识别成功本身不能建立任务、绑定正式称重、自动采集重量或提交单据。操作员核对或修改后，以“核对车牌并查找运输”完成本次车牌认可和任务查找；后续仍需称重集中核对与最终明确确认。
- **模拟识别场景**：工作台仅提供清晰标记的“模拟车辆到磅”触发入口。后台演示设置保存模拟现场车牌、候选和识别场景，预置即用示例并允许自行配置。正确场景的候选与现场车牌一致；错误场景可故意错部分字符；失败场景不产生候选并允许人工录入。识别过程是界面模拟，不调用 OCR、浏览器摄像头权限或真实设备接口。
- **画面核对依据**：在模拟画面中展示与本次模拟车辆对应的清晰车牌特写，供操作员对照候选核对。固定车辆示例照片和模拟车牌特写如采用组合展示，须清楚说明是模拟画面，不能声称原照片实际拍到了配置车牌。每次已确认称重对应的模拟现场信息、候选和人工结果保留当时快照，不随后续演示配置变化。
- **当前车辆保护**：操作员开始编辑、核对或已经定位／采集后，新识别结果只能提示，不得覆盖当前输入、任务、草稿或采集。由操作员完成当前办理并明确进入下一辆，才接入下一辆候选。本轮不增加车辆排队调度系统。
- **称重流程复用**：保留同车未结束任务匹配、方向决定毛皮语义、先采集后补资料、首磅一次确认建任务、回磅一次确认出测试单的规则。同车补业务资料不清除仍有效采集；定位后修改车牌须重新查找，原采集及抓拍失效。现场失稳、超时、断网、设备／证据异常及当前任务失效继续按原规则阻止确认；资料或核对依据变化使旧核对会话失效。
- **重量及后续处置**：所有业务重量统一为吨，精确至 0.001 吨，展示省略末尾无效零。回磅沿用原始值只读、最终毛皮重输入、系统反算扣减及净重规则，固定底栏保留最终毛皮净重与确认动作。不修改重称、任务终止、作废、更正重开、补打、未知提交恢复及有效单唯一规则。
- **识别来源与历史**：在每次称重依据中保留当次原候选、人工确认值和模拟识别／人工录入来源；修改候选不覆盖原候选。详情可查相应依据，首磅与回磅分别保留。确认前的识别修正不要求额外原因；确认后的业务纠错沿用主管权限、既有原因和留痕规则。后续主管纠错或更正重开不得改写原次识别及称重证据。
- **同源标签协作**：独立工作台与后台共享本浏览器中的模拟业务数据，后台新增资料自动更新工作台候选，保留当前输入及有效采集。仅打开后台、加载缓存或收到无关资料更新，不得清空现场进度；实际修改当前任务或模拟现场条件，则提示并使相应旧核对／采集失效。持久化与状态更新复用既有业务命令入口，防止后台旧内存快照覆盖另一页已保存的数据。具体同步机制采用满足本场景的简单方案，不扩展为正式分布式会话系统。
- **登录与权限**：沿用已有登录、JWT 和用户管理契约；独立页面继续受鉴权保护。模拟岗位不冒充真实业务授权，不以页面独立为理由重构权限体系。
- **缓存兼容**：保留已存在的测试任务、单据、图片、草稿与历史。新示例采用可用于新控件的普通／新能源车牌；旧示例或缓存中的特殊测试车牌不得被静默改写、丢弃或伪造成新识别结果。兼容读取与继续查询既有数据，必要的编辑适配通过显式核对和既有纠错流程处理，不以清库解决兼容。缺少历史识别信息时如实留空或标记未记录。刷新工作台后保留可恢复草稿，未确认现场采集按既有规则重新取得；未知提交继续优先查询原结果。
- **文档同步**：实施时更新当前阶段范围和工作台页面设计说明，将原“本阶段车牌仅手填”的限制修订为“前端模拟识别候选并人工核对，真实识别仍未实现”。保留既有交付记录的历史事实，记录新页面对后台布局规则的局部覆盖。

## Testing Decisions

- **用户已选择**：以浏览器流程测试为主，减少核心测试。不把上述用户故事逐项转换成端到端测试，不增加测试框架，也不为组件内部状态、DOM 分格实现或同步机制内部细节编写镜像测试。
- **主要测试入口**：复用现有 Playwright 页面冒烟方式，以用户可观察的完整流程为主要验收边界；扩展少量场景，在同一浏览器上下文中实际操作后台与工作台多个页面。界面断言关注最终显示、任务匹配、草稿保留、已保存业务记录和可执行操作，而非私有实现。
- **真实导航与外壳**：新增工作台入口、路由外壳和窗口复用涉及原页面 fixture 未覆盖的行为，必须使用实际菜单／入口、实际路由以及独立外壳验证。已有轻量测试页面可以复用真实组件和本地登录测试状态，但不能用手写的替代链接或假外壳来证明这些行为通过；也无需为此接入真实称重服务端。
- **场景一：独立页面与后台协作**：从后台菜单打开工作台、再次点击复用、关闭后重开、从任务入口定位、查询／维护时不离开当前工作台。实际在后台补物料并返回，验证候选自动更新且草稿和有效采集保留；接续在另一页保存业务动作，验证不存在用旧页面快照覆盖新记录。现场模拟条件变化则使旧采集失效，并可重新采集继续。
- **场景二：车牌与模拟识别闭环**：组合覆盖省份选择、连续输入、完整粘贴及大写转换，并使用普通与新能源示例。演示正确候选、错误候选修改及识别失败后人工录入；人工核对前不定位任务／提交称重。编辑或已采集期间注入新候选，验证只提示而不覆盖；改牌后旧采集不能确认。查看首磅／回磅详情，核对当次候选、确认结果及来源未被后续设置覆盖。
- **场景三：称重回归与显示**：在上述流程中复用现有首磅／回磅、最终重量调整、集中核对取消、提交结果未知和下一辆场景，覆盖两方向的代表性流程。继续复用既有原始异常与恢复验证。抽查旧缓存没有被清空、历史来源没有伪造、主管纠错／更正重开使用专用车牌控件且仍受原规则约束。
- **视觉与操作验证**：检查 1366×768 桌面和约 390px 窄屏；复核画面三档大小、放大、键盘操作、弹窗焦点恢复、固定确认区和无横向溢出。实际截图自检，确认界面能辨认模拟现场车牌、识别候选及当前办理阶段。全屏不能自动化覆盖的环境限制如实记录，并补简短人工检查。
- **既有核心测试**：运行现有称重公开命令行为测试作为回归，保留非法状态转换、重量计算、重复确认和历史证据等原有覆盖。只有关键业务边界不适合由上述浏览器场景可靠验证时才少量补充；不为每个号牌字段或识别状态新增一套单元测试。
- **验证入口与适用范围**：前端实施后运行规定的 lint、build、现有称重核心入口与受影响的浏览器冒烟。菜单／路由专项仅针对本次确实改变的公共行为选取，不默认重复所有无关专项。浏览器服务设置超时并清理；本规格当前仅做文档检查，不声称新增功能已通过实现测试。

## Out of Scope

- 真实摄像头视频、RTSP、HyperLPR3／其他 OCR、真实车牌识别准确率、置信度及识别算法调优。
- 真实仪表重量采集、物理打印、现场 Agent、WSS、正式业务 API、数据库业务表、正式称重记录和正式电子过磅单。
- 特殊牌型的完整覆盖及真实机动车登记状态核验；本轮新输入面向普通和新能源车牌，历史特殊测试字符串按兼容规则保留。
- 多车排队调度、多地磅业务、真实跨终端／跨浏览器协作及生产级并发占用机制。
- 后台通用标签页系统、全站视觉重构、JWT／用户／权限体系重构和依赖升级。
- 自动确认车牌、自动确认称重、自动生成正式单据、断网正式出单或把历史缓存自动补为正式记录。
- 改变人工重量调整、原始／最终双列表、打印与补打、主管业务处置等已确认规则。
- 独立的多层测试平台、逐条用户故事自动化、与用户可观察行为无关的实现细节测试。
