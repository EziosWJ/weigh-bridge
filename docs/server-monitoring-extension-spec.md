# Spec：服务器监控可选启用、Windows 原生采集与网卡 IP 展示

已发布：[Spec #77](https://github.com/EziosWJ/base-project-golang/issues/77)，标签：`ready-for-agent`。

## Problem Statement

管理员需要在 Windows Server 上查看本项目所在服务器的资源状况，并通过网卡 IP 地址确认具体网络接口。目前服务器监控的正式采集仅支持 Linux，网卡列表没有 IP 地址，Windows 平台返回不支持状态。

脚手架使用者不一定需要资源监控，但当前 API 启动会持续采集并维护历史。完整监控包含进程排行、GPU、异常提示和宿主机采集进程，增加部署及跨平台维护成本。使用者需要能够按需启用，默认不承担后台采集成本。

## Solution

把服务器监控定位为脚手架的可选能力，默认关闭。显式开启后，保留现有 Linux 监控，并支持在 Windows Server 2019/2022 上原生运行 Go API、采集 API 所在主机的资源。

Linux 与 Windows 的网卡列表均提供“查看 IP”按钮，通过模态框展示所选网卡的全部 IPv4/IPv6 地址及前缀长度。地址随现有监控快照更新，无地址时明确展示“未分配 IP”。

关闭时不启动采集、不维护监控历史、不展示服务器监控菜单，直接访问监控接口得到明确的模块未启用响应。沿用现有 ADMIN 授权和单台宿主机边界。

## User Stories

1. As a 脚手架使用者, I want 默认关闭服务器监控, so that 未使用该能力时无需持续进行资源采集。
2. As a 部署者, I want 通过启动配置显式开启服务器监控, so that 可以按项目需要选择该能力。
3. As a 部署者, I want 沿用现有 YAML 与环境变量配置机制, so that 无需维护新的配置来源。
4. As a 脚手架使用者, I want 关闭监控时不创建采集任务和监控历史, so that 可选能力不会持续消耗采集和历史存储资源。
5. As an ADMIN 管理员, I want 关闭监控时隐藏服务器监控菜单, so that 导航不会引导我进入未启用功能。
6. As an ADMIN 管理员, I want 直接访问关闭的监控页面时看到模块未启用, so that 可以理解功能当前不可用的原因。
7. As an API 调用者, I want 关闭监控时接口明确返回模块未启用, so that 可以区分功能关闭、采集故障和权限错误。
8. As a 系统维护者, I want 开关只控制资源监控模块, so that 应用存活、数据库就绪和应用指标继续正常工作。
9. As a Windows 部署者, I want 在 Windows Server 2019 上原生运行 API 并采集该主机, so that 可以排查项目所在 Windows 服务器的资源瓶颈。
10. As a Windows 部署者, I want 在 Windows Server 2022 上使用同样的监控能力, so that 可以在已确认的目标系统上部署项目。
11. As a Windows 部署者, I want 原生采集复用现有 native 模式, so that 无需部署新的远程采集服务或通信协议。
12. As an ADMIN 管理员, I want 页面正确显示 Windows 主机身份、系统信息和运行时长, so that 可以确认正在查看的服务器。
13. As an ADMIN 管理员, I want 查看 Windows CPU 型号、核心数和总体及逐核利用率, so that 可以判断 CPU 资源瓶颈。
14. As an ADMIN 管理员, I want 查看 Windows 物理内存总量、已用、可用和占用率, so that 可以判断剩余内存承载能力。
15. As an ADMIN 管理员, I want 查看 Windows 卷或挂载点的容量, so that 可以发现接近用满的存储空间。
16. As an ADMIN 管理员, I want 查看 Windows 磁盘读写速率和 IOPS, so that 可以判断存储读写压力。
17. As an ADMIN 管理员, I want 查看 Windows 各网卡的流量和可用链路信息, so that 可以排查具体网络通路。
18. As an ADMIN 管理员, I want 查看 Windows CPU 和内存进程排行, so that 可以定位主要资源占用进程。
19. As an ADMIN 管理员, I want 在具备 NVIDIA 设备和采集条件的 Windows 主机上查看 GPU 指标, so that 可以了解各卡资源状况。
20. As an ADMIN 管理员, I want 系统不支持或权限不足的字段显示原因, so that 不会把缺失数据误认为零占用。
21. As an ADMIN 管理员, I want Windows 页面沿用现有历史和异常提示, so that 不同平台具有一致的排查流程。
22. As an ADMIN 管理员, I want 在 Linux 网卡列表点击“查看 IP”, so that 可以确认所选接口的地址。
23. As an ADMIN 管理员, I want 在 Windows 网卡列表使用相同的 IP 查看操作, so that 无需学习另一套交互。
24. As an ADMIN 管理员, I want 弹窗显示网卡名称, so that 可以确认地址所属接口。
25. As an ADMIN 管理员, I want 查看所选网卡的全部 IPv4 地址, so that 不会遗漏多地址配置。
26. As an ADMIN 管理员, I want 同时查看该网卡的全部 IPv6 地址, so that 可以检查双栈和 IPv6 网络配置。
27. As an ADMIN 管理员, I want 地址显示地址族和前缀长度, so that 可以识别地址类型及所属网段。
28. As an ADMIN 管理员, I want 无地址的网卡显示“未分配 IP”, so that 可以区分确实没有地址与读取失败。
29. As an ADMIN 管理员, I want 打开的弹窗随监控快照更新地址, so that 网卡地址变化后可以看到最新结果。
30. As an ADMIN 管理员, I want 继续使用现有网卡筛选规则, so that IP 功能不会改变默认网卡列表范围。
31. As an ADMIN 管理员, I want 采集失败或过期时仍看到明确状态, so that 不会把旧 IP 和旧指标当作最新结果。
32. As a Linux 部署者, I want 本次扩展保持原生和 Unix socket 宿主机采集正确, so that 开启监控后现有部署仍可使用。
33. As a 系统维护者, I want 菜单、页面和接口继续校验 ADMIN 访问权限, so that 主机、进程和 IP 信息只向有权用户开放。
34. As a 部署者, I want 文档说明默认关闭以及如何开启, so that 升级后不会误认为监控消失或损坏。
35. As a 部署者, I want 明确 Windows 编译、自动化测试与真机验证的分别结果, so that 可以判断目标环境是否已经得到实际验证。
36. As a Windows 部署者, I want 文档明确原生部署及必要读取权限, so that 可以按实际支持的方式启动和维护采集。

## Implementation Decisions

- 本规格是现有服务器监控规格的增量：增加 Windows 原生采集、网卡 IP 和可选启用，不重新建设监控模块。
- 沿用 ADR-0011 的单台宿主机边界：原生部署采集 API 所在主机；Linux Docker 部署继续通过同宿主机采集进程和 Unix socket。正式采集平台在原有 Linux 基础上扩展至 Windows Server 2019/2022 的原生 API 部署。
- 在现有启动配置增加 `monitoring.enabled`，默认 `false`，沿用 YAML 分层和 `APP_` 环境变量覆盖机制。此为启动时开关，调整后重启 API 生效，不增加管理页面动态开关。
- 所有随仓库提供的运行配置及部署示例明确默认关闭；启动文档提供显式开启方式，并说明此次默认行为变化。
- 关闭时不得创建或初始化实际采集器、启动后台采样、维护监控历史或连接宿主机采集进程；监控采集器的可用性不得成为关闭状态下 API 启动的前提。现有独立宿主机采集进程仍由部署者按需启动，不由 API 自动启动或终止。
- 关闭时隐藏服务器监控菜单；若“系统监控”目录因过滤变为空，按现有导航规则处理，不隐藏其他有效菜单。后端需使菜单响应反映当前实例启用状态，前端不能自行猜测服务器配置。
- 监控概览和历史接口在关闭状态下，对已授权 ADMIN 返回 HTTP 503 和稳定可识别的“模块未启用”错误；不返回成功的空快照。保留原有认证及 ADMIN 授权语义，未登录和无权访问仍按原契约拒绝。
- 前端直接进入关闭的监控路由时展示未启用状态，清除已有监控数据并停止该页面的监控轮询；后端启用状态必须作为事实来源。
- 开关仅作用于资源监控；不改变应用存活、数据库就绪、Prometheus 应用指标及其他业务模块。
- Windows 原生采集沿用 `native` 数据源和已有采集接口，平台相关读取逻辑隔离在采集边界；不把系统分支扩散到 HTTP、业务规则或页面。具体采集依赖在实现时按指标需求选择并说明原因，不预先引入新的外部服务。
- Windows 指标目标沿用现有主机、CPU、内存、文件系统、磁盘 I/O、网络、进程排行和 NVIDIA GPU 分区。保留跨平台一致的计量单位、CPU 归一化、内存口径、采集时间、历史与异常规则。
- Windows 文件系统以真实卷和挂载点表达，不伪造 Linux 设备路径。Linux 系统负载 1/5/15 分钟在 Windows 中明确不支持，不用其他指标冒充；分页文件数据不得在语义不一致时直接标成 Linux Swap。
- 区分无设备、不支持、采集失败、权限不足和过期，字段无法读取时保留有效的其他字段并说明原因。核心 CPU、内存、存储和网络采集必须实际实现，不能以整个平台返回不支持替代 Windows 支持。
- 继续每 5 秒采样、每 5 秒刷新概览和历史，页面关闭后在模块启用时持续采集；保留 30 分钟实例内存历史、15 秒过期、超时与任务不重叠的现有契约。速率首次采样及计数重置重新建立基线，不填入伪造的零值。
- 网络快照按网卡增加 IP 地址集合，每项包含地址族、IP 和前缀长度，可直接呈现 CIDR。支持同一接口的多个 IPv4/IPv6 地址，接口与地址必须对应同一宿主机及同一网络范围。
- Linux Docker 路径由宿主机采集进程读取并传递网卡地址，API 容器不能用自身接口地址填充宿主机网卡。
- 地址随现有网络快照采集和传输，不增加单独的 IP 查询接口或弹窗轮询。真实无地址返回空集合；地址读取失败必须有错误或部分失败说明，不能呈现为“未分配 IP”。采集失败保留旧地址时沿用旧值与过期提示。
- 网卡表格增加“查看 IP”操作，弹窗显示网卡名称、IPv4/IPv6 与 CIDR 地址；无地址时显示“未分配 IP”。以稳定网卡标识关联当前快照，弹窗打开期间随快照更新；接口消失时明确提示接口已不可用，不继续把旧地址展示为当前配置。
- 沿用现有网卡列表筛选和显示全部接口行为，不新增地址过滤规则；当前列表中可见的回环或虚拟接口同样支持查看 IP。
- 页面文案随实际平台展示，不再固定描述 Linux 宿主机。扩展现有 DTO、前端类型与 API 契约文档，兼容地址字段缺失的旧快照时明确不可用，避免把“未提供地址字段”当作确定无地址。
- 不新增指标持久化表或时序基础设施；开关使用运行配置，菜单启用状态按实例决定，不通过修改共享数据库中的菜单可见性表达。
- 实现时同步原有监控规格与架构说明中的平台范围及默认行为，明确这是已确认的增量，不将原首版 Linux 边界误写成历史上已经支持 Windows。

## Testing Decisions

- 主要业务验证沿用既有真实 HTTP 路由入口：组装监控服务、可控采集输入及可推进时间，断言响应、授权、字段支持状态、地址数据、历史与错误。测试外部行为，不断言私有缓存结构、具体系统调用顺序或 goroutine 数量。
- 现有监控 HTTP 测试已覆盖 ADMIN 撤销、401/403、部分失败、采集时间、历史缺口和异常持续时间；扩展这些先例，不创建另一套通用测试框架。
- 配置与应用启动边界验证默认关闭、显式开启、YAML/环境变量覆盖，以及关闭时不会执行采集或访问 Unix socket、不会创建监控历史；通过可观察的采集调用与 HTTP 结果验证，而非依赖进程内部实现细节。
- 从实际菜单查询与监控 HTTP 入口验证关闭时菜单过滤、ADMIN 收到模块未启用响应，以及未登录/普通用户仍被拒绝；涉及数据库菜单契约的场景沿用临时 PostgreSQL 和 SQLite 测试环境，禁止连接实际部署数据库。
- 采集器验证复用现有采集边界，针对平台相关计数输入验证 CPU、内存、存储、网络和进程结果，覆盖首样本、计数重置、读取权限不足和部分失败。仅在系统 API 不能确定性驱动时增加局部输入边界，不引入新的全局任务框架。
- 覆盖 IPv4、多 IPv4、IPv6、双栈、不同前缀长度、回环/虚拟接口、无地址、地址读取失败、地址变化和接口消失；断言地址属于正确网卡，错误不被转换成“未分配 IP”。
- 扩展既有 Unix socket 往返测试，验证地址信息及原采集时间完整传递；保持断开时不回退采集 API 容器的既有行为。Linux 原生与 Docker 宿主机路径均做针对性回归。
- 前端沿用现有 Playwright 监控浏览器验证，通过可控 HTTP 响应覆盖按钮、弹窗、多地址、CIDR、空地址、快照更新、过期/失败、接口消失，以及 Windows 主机文案。验证关闭时菜单隐藏、直接路由访问、旧数据清理与停止轮询；保持 ADMIN 权限及页面卸载清理的既有断言。
- 执行项目统一入口：`task backend:check`、`task frontend:lint`、`task frontend:build` 和 `task frontend:monitoring`。仅在相关菜单数据库集成行为变化时补充 `task backend:integration`，不为本次功能凭空创建 migration。
- 验证 Windows 目标构建并记录目标架构、数据库驱动和 CGO 条件；同时验证 Linux 构建不受平台依赖影响。编译通过、模拟采集测试和 Windows 真机采集验收分别报告，不能相互替代。
- Windows Server 2019/2022 真机验收对照系统工具检查主机身份、CPU、物理内存、卷容量、磁盘 I/O、网卡流量/IP 和进程排行，记录读取权限、未支持字段及观察结果。NVIDIA 需要实际设备与驱动环境验证，记录支持字段；没有对应环境时明确标记未验证，不宣称已通过。
- 长时间联调使用超时、健康检查和清理；应用 `/health` 验证存活、`/ready` 验证数据库就绪。未执行的检查和缺失的真机验证作为交付限制明确记录。

## Out of Scope

- Windows Docker Desktop 中的 API 监控外部 Windows 宿主机、WSL 代表 Windows 主机的采集承诺，以及新的 TCP/命名管道采集协议。
- 多台服务器、远端采集注册、远程主机管理和跨实例共享历史。
- macOS 正式采集支持；Windows Server 2019/2022 之外版本的正式支持承诺。
- 新增指标种类、AMD/Intel GPU 正式支持，以及原有监控之外的硬件管理能力。
- 超过 30 分钟的持久历史、时序数据库、Redis 或外部监控平台。
- 页面动态启停开关、运行中热重载、手动暂停采集及新的地址刷新周期。
- 修改网卡 IP、启停设备、终止进程、自动修复、远程运维操作。
- 新增告警通道、用户自定义异常阈值、Ping/端口/HTTP 可用性探测。
- 删除现有 GPU、进程、历史或异常功能以裁剪模块，以及对相邻模块进行无关重构。

## Further Notes

- 需求依据：本次访谈中用户接受 Windows 原生部署、Windows Server 2019/2022、沿用指标与缺失原因展示、IPv4/IPv6/CIDR 弹窗、现有快照刷新，以及模块默认关闭的建议。此规格仅综合既有对话，不另开需求访谈。
- 前置规格：[Spec #64：Linux 宿主机资源监控面板](https://github.com/EziosWJ/base-project-golang/issues/64)。本规格扩展其正式平台范围并调整默认启用行为，其余既有契约继续沿用。
- 本次调查时，[进程 Top 10 #70](https://github.com/EziosWJ/base-project-golang/issues/70) 与 [NVIDIA 多卡 #71](https://github.com/EziosWJ/base-project-golang/issues/71) 仍为开放状态；工单状态不等于能力完成或缺失，实施前核对已有代码与验收记录，避免重复实现或把未验证能力当作已验收。
- 服务器监控的功能与跨平台维护成本对通用脚手架偏高；默认关闭降低不使用时的运行负担，但不意味着移除跨平台维护成本，也不构成运行开销已经实测的结论。
- 本规格发布为 `ready-for-agent`，不附带实现工单拆分，不声称实现、Windows 真机验收或性能测试已完成。
